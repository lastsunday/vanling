# 回声消除实现记录

`apps/iot/crates/core/src/drivers/aec/` 的实现判断与被否方案。**AI 产出，未经人类审阅**，见[上级说明](@/records/_index.md)。

每条判断标注依据：**`[测试]`** 有对应单元测试，**`[实测]`** 有测量并附复现方式，**`[据称]`** 未复现、仅留痕。

线性 AEC 只做一件事：把扬声器送出的样本所经声学路径建模出来，从麦克风里减掉。非线性抑制不在其中——见 `aec/mod.rs` 的模块文档。

**本文顺序：先算法验证，后硬件代价。** 这两件事的因果曾被我弄反过一次——先测了 CPU，然后拿一个合成房间的数字去证明算法行。顺序反过来才对，因为「算法值不值得做」决定「要不要为它花 CPU」，反过来不成立。

---

## 没有可用的公开录音做验证：三份实测不可用，第四份誊录不可验证

`[实测]` 计划要求「用官方测试向量量出定点线性 AEC 能压下多少 dB」。找遍之后：**不存在一份干净的、含真实线性声学回声路径的 (参考, 麦克风) 公开录音。**

**乐鑫 `docs/_static/aec_in_far.wav` / `aec_in_near.wav`。** 标注为「远端（播放参考）」与「近端（含回声的麦克风）」，是读者第一个会拿的文件。**两者不同步**：全程 53 s、遍历所有滞后，最大归一化互相关 **0.137**；单抽头拟合只解释 **0.08 dB**；包络相关 0.35；谱质心 1301 Hz vs 2620 Hz。本实现在这对上得到 **−14.4 dB**——正是「减掉一个不相关的信号」应有的结果。

**乐鑫 `audio_mic_file` / `audio_ref_file`。** 这是乐鑫自己 `test_afe.cpp` 喂给 `aec_process` 的一对，同步（相关 0.743，单抽头增益 0.9956）——**但里面没有回声路径**。离线最小二乘（任何平稳线性抵消器的上界）：

| 抽头 | 全程 ERLE | 核峰位置 |
| --- | --- | --- |
| 32 | −1.04 dB | 1.02，落在**最后一抽** |
| 64 | +0.04 dB | 1.03，落在**最后一抽** |
| 128 | +0.42 dB | 1.02，落在**最后一抽** |
| 256 | −4.97 dB | 1.02，落在**最后一抽** |

能量压在窗口末尾那一抽、无衰减结构、无体延迟——不是声学路径。前半段拟合后半段测试得 +5.08 dB（样本内 +6.15 dB），关系是持续存在的，只是不是回声。

**Microsoft ICASSP AEC-Challenge 的 `real_doubled`。** 本领域真正的参考数据集，10,000 个真实环境。**扫了 40 个 GUID，没有一个有线性回声关系**：128 抽离线 Wiener 上界最好的是 **−0.42 dB**，任何位置的最大相关 0.137。**这是有据可查的行为**，Cutler 等《ICASSP 2023 AEC Challenge》(arXiv:2309.12553) §4.1：

> Even though our application uses the WASAPI raw audio mode to bypass built-in audio effects, the PC can still include Audio DSP on the receive signal [...] it can also include **Audio DSP on the send signal, such as AEC and noise suppression**.

消费级音频栈若在环回抽头和落盘文件之间**已经跑了它自己的回声消除**，线性模型就没有任何东西可预测。同一节说明 ERLE 也不是这份数据集的指标（**与主观质量 PCC 仅 0.31**）。

**ITU-T G.168 (04/2015)** 是下一个答案，而且方向完全正确：Annex D 给出 8 个回声路径模型 `m_i(k)` 的**显式冲激响应表**加缩放因子 `K_i`，**参考素材确实一个字音频文件都不需要**——正是该找的东西。PDF 公开可下载（154 页）。**但没有采用**，因为誊录无法验证：

- 部分页面上表格的首列被文本抽取吞掉（m1 每行的第一个数与同行其余数差 1–2 pt 基线）
- 读取顺序有歧义（"to be read in columns"），列主序与行主序两种读法差一倍
- **两种读法都违反标准自己的不变式**——「缩放后 g(k) 的幅度响应不得超过 0 dB」——超出 1 到 11 dB

验证不了的表格不是测试该建立其上的数据。这和删掉软件时钟标定是同一个理由：**交付站不住的数字比不交付更糟**。

不过 G.168 的 Test 12 注记替我方结论盖了章：

> This test may be enhanced by the future addition of test vectors that represent real acoustic echo signals. **This enhancement is for further study.**

**标准机构自己说真实的声学回声测试向量还不存在。**

### 于是参考基准改为「同一条路径上的离线最优」

不是借用一条外部路径，而是对每条路径**当场解最小二乘**，报出**同样长度下任何滤波器能达到的最好结果**。这个数是算出来的不是誊来的，所以不可能错，而且它回答的是线性自适应滤波器真正要回答的问题：**它找到最优线性解了吗，差多少？**

复现（无外部资产、无网络）：

```sh
cd apps/iot && cargo test -p iot-core --test aec_erle -- --nocapture
```

| 路径 | 抽头 | 离线最优 | 本实现 | 差距 |
| --- | ---: | ---: | ---: | ---: |
| 短，快衰减 | 16 | 62.9 | 61.0 | 1.9 |
| 中等，中等衰减 | 48 | 58.8 | 57.2 | 1.6 |
| 长尾，慢衰减 | 192 | 38.9 | 38.8 | **0.1** |
| **尾长于滤波器** | 256 | **14.4** | 13.2 | 1.2 |

### 15 dB 那道闸被重新定义了：它是对路径说的，不是对算法说的

**尾长于滤波器时，离线最优本身只有 14.4 dB** —— 任何 128 抽线性滤波器都到不了 15 dB。要求算法到达 15，是要求它出错。

所以验收判据从「固定 dB」改成「**与离线最优的差距 ≤ 3 dB**」，而 15 dB 只施加在**滤波器能完整容纳的路径**上。这条区分是自验证基准才给得出的：借来的路径告诉不了你上限是谁设的。

同时保留两条限制：**过了 15 dB 是必要不充分**（PCC 0.31）；**这些路径是生成的，测的是契约不是房间**，本板的回路增益、体延迟、门限仍需板子。

## 生成路径必须有直达反射，否则延迟搜索无处可寻

`[实测]` 第一版路径的**每一个抽头都是同量级随机值**，于是没有「起点」——每个滞后的相关都差不多，延迟搜索锁不住任何东西，只会报噪声碰巧最大的位置：12 抽的路径报 15，4 抽的报 22（离线核对确认峰值本来就在那里），滤波器瞄错地方，只拿到 **0.4 dB**。

真实的房间冲激响应有**一个明确的直达反射**压过其后所有反射。补上（直达 30,000、其后 ±8,000）之后，四条路径的互相关峰**精确落在真值上**（8/12/6/4），ERLE 随之从 0.4 dB 变成 61 dB。

同类的错误在断言里也出现过一次：原本测「说话人没被学成回声」的指标是**滤波器能量落在路径之外的占比**，而一条 48 抽路径配 128 抽滤波器，路径之外本来就有 46% 的能量（很多小系数）——**该测的是增长量，不是占比**。

## 冻结拦得住持续损伤，拦不住起始那半秒

`[实测]` 这是新测试逼出来的。相干度计量器的时间常数约 512 样本，所以说话人开口后，滤波器仍以**全速**自适应了约 543 个样本，然后冻结锁定了状态。

| | 值 |
| --- | --- |
| 冻结覆盖 | 31,457 / 32,000 样本（98%） |
| 路径外能量，静默时 | 3.203e10 |
| 冻结生效时 | **1.176e17（3.7e6 倍）** |
| 结束时 | 1.176e17（**冻结之后没有再增长**） |

所以设计是**部分**有效的：冻结确实止住了损伤增长，但它止不住第一段。Q30 下这对应约 3.6% 的增益被学进了本该为零的抽头——不是 0，但也不是零。

**根因是计量器的滞后，不是门限。** 相干度要几百个样本才读得出「不相干」，而滤波器在这几百个样本里已经跑完。缩短保持窗口解决不了（相干度还是那么慢）。真正的修法需要一条**更短的冻结决策专用计量器**，那是设计改动，不在验证这一轮里做。

`[据称]` 听感上这半秒有多糟，没有在本板测过。

## 步长不能按残余电平缩放

`[实测]` Valin 的变步长 MDF/NLMS（TASLP 2007）确实按残余缩放步长，这也是「从残余推导步长」最自然的读法。**但在收敛之前，残余就是麦克风本身**——它不是一个和滤波器有关的量，它是房间里最响的东西。

在 12 000 LSB 的合成房间上，这把起始步长压到全速的 1/48，滤波器得到 **−0.5 dB**；同一套循环换成固定全速步长得到 20 dB。慢启动不是「精度差一点」，是整个收敛过程都没发生。

所以 `learning.rs` 里的步长是**常数**：全速，或者冻结时为零。残余只用于它能唯一回答的那一个判断。

「全速」是选出来的，不是默认值：NLMS 在 `(0, 2)` 内稳定，`1 << 29`（Q30 的 0.5）是常规选择，下面还有余量。

---

## 冻结不能只看残余电平：收敛中的滤波器和一个说话的人留下的都是大误差

`[测试]` 这是上面那个失败从另一侧撞上来的同一件事。绝对门限作用在残余上，会在滤波器自己的启动过程中把它冻住。

分开这两者的量是**相干度**：

- 滤波器还在收敛时，误差主要是**它还没解释掉的那部分回声**，因此与参考高度相关（相干度 ≈ 1）；
- 有人说话时，误差是语音，与参考几乎无关（相干度 ≈ 0）。

这是 Gänsler 的相干度双讲检测（JASIP 2015 指出它的两个缺点：门限依赖背景噪声与说话人音量）。它放在滤波器旁边而不是旁边再放一个检测器，是因为滤波器本来就要算的东西全在这里：三个滑动均值，每个样本多一次乘法。

`learning.rs` 的两个门限都标了 `[据称]`：`LEAKAGE_FREEZE = 1<<24`（约 4096 LSB RMS，取自[音频记录](@/records/iot/audio.md)里 30 cm 语音峰值 80 dB SPL 的标定）、`MAX_COHERENCE = 0.6`。两个都要在台架上用真人重测。

**`has_path` 这一层被删掉了。** 它用「预测量够不够大」代替相干度，而一个把麦克风整个预测出来的滤波器预测量也很大——它其实什么都没学到。相干度一个量就够。

---

## 相干度的分子是带符号均值，不是平方均值

`[测试]` `coherence = |E[e·x]| / (rms_e · rms_x)`。第一版把 `e·x` 平方后再进滑动均值，得到的是**幅度平方相干**——它分不出「路径反相」和「路径不存在」，而两者在这里要分开。

代价一样是一个乘法，收益是分得开。所以 `power.rs` 里多了一个 `SignedMeter`，和 `PowerMeter` 同一个位移、同一条理由：**截断时补 ±1 的下限是它能真的收敛到目标而不是停在半步之外的唯一办法**，而对带符号的量这件事重要两倍——到不了零的均值不是均值。

---

## `Noise::new(seed | 1)` 把相邻种子折叠成同一个序列

`[测试]` xorshift 状态为零就永久卡死，而零正是调用方最可能写下的那个种子，所以它需要被换掉。但**只需要非零，不需要奇数**。

原来的 `seed | 1` 把 2 折成 3、把 3 折成 3。于是「两个独立的噪声源」其实是同一个信号，相干度读 1.0，而正确的值是 0。这个 bug 的危险在于它完全静默：测试照跑，只是断言了一个假的数。

`signal.rs` 里现在有一条测试专门钉住它。

顺带：同一次重写里还发现测试生成器用 `i32` LCG 配 `n >> 16` 做均匀噪声是错的——算术右移让一半的值变负，`% 16000` 保留符号，再减 8000，样本范围变成 [−24000, −1]，均值平方大 6.8 倍，冻结门限因此形同虚设。现在统一用 `signal::Noise`。

---

## 延迟搜索必须有置信度门限

`[测试]` 比窗更远的路径，在窗内每个滞后上的相关都约等于零，而搜索返回的是**最大的那一个**——也就是噪声里的最大值。功率门限挡不住这一种：两个不算静音的房间照样能找到一个峰。

没有门限时，超出搜索范围的路径被回答成窗内某个随机的数（实测报 2，真值 84），而调用方无从分辨。加 `MIN_CORRELATION = 300`（千分比）之后同样的输入回答「没找到」，`settled()` 保持 false。

窗外的路径返回窗边缘同样不对——那是一个看起来很确定的错数。现在返回 `None`。

---

## 延迟搜索必须限频：它比用它的滤波器还贵

`[实测]` 搜索一次是 `(2·SEARCH + 1)·WINDOW = 65 × 256 = 16,640` 次乘加，约等于自适应滤波在同样本上工作量的三分之二。**每个样本都跑，找到延迟会比用它抵消更贵。**

延迟是板子放在哪里的属性，不是音频的属性，所以按 40 ms 一次（`REFRESH_SAMPLES = 16 × WINDOW`）。首次搜索在历史攒满时立即发生，不等一个间隔——延迟是最该早拿到的量。

加之前 `cargo test -p iot-core aec` 要 45 s（851,940 样本上跑成平方复杂度）；加之后 0.14 s。`DelayEstimator::searches()` 报告实际搜索次数，因为提高这个速率的人有权知道自己买到了什么。

---

## ERLE 的稳态值和全程值不是同一个量

`[实测]` 同一段音频、同一套滤波器，两个数都不是错的，只是回答不同的问题。**AEC Challenge 的规则与此一致**（Cutler 等，§7）：

> For the far end single talk scenario, we evaluate the **second half** of each clip, to avoid initial degradations from initialization, convergence periods, and initial delay estimation.

所以**只报后半程是标准做法**，全程数降级为附带。

第一版把「全程求和」和「末态瞬时读数」放在一起比，差 51 dB，然后花时间去怀疑仪表。真正的教训是：**收敛过程和稳态必须分开报**，否则其中一个必然被当成另一个。逐秒曲线（16 → 19 → 21 dB）是它收敛多快的证据——一个只报终点的数字分不清「收敛很快」和「二十秒后才收敛」，而这个差别决定电话的前半程能不能用。

计量器自身的读数（63.0 dB）与样本求和（57.2 dB）差 6 dB，在容差内；两者的窗口不同，一个是 ~30 ms 的指数平均，一个是整段求和。

## 数字上踩过的几处

`[测试]` 都是先错了、后被测量推翻、再改的：

**`PowerMeter` 的步长下限不能用 `max`。** `max` 取**较大**的那个值，于是电平下降时每样本走 1 LSB 而不是 2⁹，计量器把电平多保持约 1000 倍。残差停在 389 而真值是 900。正确做法是仅在移位结果为零时取 ±1。

**环形缓冲要先推进再写入。** 否则 `head` 指向最新样本的下一个槽，`tap(0)` 读到错位一格，每个峰都晚一抽落地。

**整数 `log2` 的尾数提取。** 平方尾数时进位位必须和被缩放的值分开处理：进位用 `squared >> 1`，不是 `squared >> (LOG_FRACTION+1)`。

**`ErleMeter` 的比值不要用 Q 缩放。** 分子乘 2¹⁶ 之后会从对数里多出 16 个八度。整数除法截断误差不到 0.5 dB。

**保持计数器必须封顶。** `above` 自由增长会在长段说话时饱和到 `u32::MAX`，之后每个样本只减 1，再也解不开——滤波器永久冻结。

## CPU：先量时钟，再谈结论

`[实测]` 第一版这里贴了一张我站不住的表。它说 L=128 要 74.7 ms/tick、「219 cycles/MAC」，并用一条数据手册上的时钟去换算。**两处都错了，错在同一个根上：我从来没读过这颗芯片实际被配成了多少。**

### 参照循环揭穿了它

探针里加了一条尽可能平凡的循环：256 系数 × 1024 样本的**整数** FIR，无边界检查、不走 `&mut self`——**就是 Espressif 公开基准 `dsps_fir_f32` 的原题**，所以数字可以直接对。

我预期它跑在 1.7 cycles/MAC 附近。实际 **12 cycles/MAC**。一条比 AEC 滤波器更简单的循环慢 193 倍，说明问题不在 AEC 的代码。

### CPU 跑在 80 MHz

`esp_hal::clock::cpu_clock()` 读回 **80,000,000 Hz**。原因在 esp-hal 1.2 自己的源码里：

```rust
pub enum CpuClock {
    /// 80 MHz CPU clock
    #[default]
    _80MHz  = 80,
```

`Config` 派生 `Default`，`CpuClock` 的默认臂就是 `_80MHz`。**`esp_hal::init(Config::default())` 给的是 80 MHz。** 我先前引用的「`Config::default()` 会设到最高频率」来自一篇讲 Arduino-ESP32 的博客，不是 esp-hal。

换成 80 MHz 重算，参照循环 12 cycles/MAC，而 Espressif 的**浮点**汇编在 240 MHz 是 1.69 —— 折到 80 MHz 是 36。**我的整数循环比它还好。平台、时钟、计时器、构建全部正常。**

### 修正后的数字

| | µs / tick (L=128) | cycles/MAC @80 MHz |
| --- | ---: | ---: |
| **参照 FIR**（平凡整数循环） | — | **12** |
| AEC 卷积 | 16,206 | 31.6 |
| **AEC 系数更新** | 48,941 | **119** |

**不是 219。** 但「5.4 倍来自边界检查和 `&mut self` 栈重装」这个归因**也是错的**——下一节。

### 分块自适应：过了

系数更新是最大的单项——L=16 的 7.7 ms、L=128 的 49 ms——而每样本更新一次不是必须的。改成每 4 个样本一次（`UPDATE_STRIDE`，用 `head % 4` 计数，不加任何状态）。

`[实测]` **L=16 从 15,531 掉到 9,680 µs，过了 ≤10 ms 那条线。**

| | 逐样本 | stride 4 |
| --- | ---: | ---: |
| L=16 系数更新 | 7,699 µs | **1,880 µs**（−76%） |
| L=16 滤波器整体 | 9,803 | **3,945**（−60%） |
| **L=16 整体** | 15,531 | **9,680 µs** |
| L=32 | 22,892 | 13,528 |
| L=64 | 36,772 | 20,448 |
| L=128 | 70,945 | **34,911 µs**（−51%） |

代价在 ERLE 上：**稳态逐位不变**（四条路径对离线最优的 gap 仍是 1.9 / 1.6 / 0.1 / 1.2，移动路径照样跟过六样本的突变），**但 whole-file 从 20.9 掉到 16.2 dB**——慢的是收敛，不是收敛之后。

卷积现在占滤波器的一半（2,065 vs 1,880），更新不再是主要代价。

### 频域路线：写完了 FFT，量出来是「否」

最佳实践指向 MDF / 分块频域 NLMS。`arduino-audio-tools` 恰好把两套并存（时域 NLMS 与 speexdsp 的 MDF 移植），对时域那套的判词是：

> O(filter_len) work per sample, no FFT … **a reasonable fit for small microcontrollers with a short, simple echo path**
> cost grows linearly with it — **this is not the right tool for a long, reverberant echo tail**

所以按计划先写 FFT、先测它，再谈架构：512 点 radix-2 定点，旋转因子用二进制幂生成（递推相乘会漂，逐项 ≤9 次舍入），7 个测试，其中一个拿独立的 f64 直接 DFT 逐点对拍。

`[已删]` **那个 FFT 量完之后删掉了。**结论留下，代码没有——它在产品路径里零引用，留着就是一份没有调用者的代码，而记录里留着一个「变换要占预算 182%」的结论比留着一个没人用的变换更有用。**下面的数字是实测的，不是推断。**

`[实测]`：

| | |
| --- | ---: |
| 512 点正变换 | **3,046 µs** |
| cycles/蝶形 | **105.8** |
| 一个 320 样本 tick 需要 2 块 × 3 次变换 = 6 次 | **18,276 µs = AEC 全部预算的 182%** |

**变换一项就超了预算 1.8 倍**，分区卷积、滤波更新、延迟搜索一分钱都还没花。

改小帧长救不回来：每样本代价 ∝ 3·5·2M·log(2M)/M = **15·log(2M)**，M=256 是 135、128 是 120、32 是 90——**渐近到常数。**实数 FFT 打包砍一半到 9.1 ms（91%），剩下 9% 给滤波器，不成立。RAM 也要从 **3,064 B** 涨到 6 KB。

### 第二核：数字逐位相同

`FROM_CPU_INTR1` 是同一颗核上的第二个中断源（`InterruptExecutor<1>`），不是第二核——**产品固件全部跑在 core 0，core 1 完全空闲。**探针改成两个核先后跑同一份测量（不重叠，否则会抢总线）：

| | cpu 0 | cpu 1 |
| --- | ---: | ---: |
| FFT 正变换 | 3,046 µs | **3,046 µs** |
| cycles/蝶形 | 105 | **105** |
| 参照 FIR | 34,628 µs | **34,628 µs** |
| L=128 整体 | 70,945 µs | **70,945 µs** |
| 系数更新 | 48,939 µs | **48,939 µs** |

20 多项独立测量、跨 4 个抽头数、含均值和最坏值，**全部逐位相同**。

**双核一分钱都不值**，而这同时把那个悬着的诊断问题关掉了：两个独立的 LX7 核撞在同一个共享资源上，每次访问的固定延迟相同、操作次数相同，总时间必然相同。**这不是「core 0 太忙」，是两边共享的瓶颈。**

### IRAM：也不是

把蝶形单独提出来放进 `.rwtext`（链接脚本把它映射到 0x4037a4c4 的 IRAM 区，确认不是 flash 的 0x42010020）：

| | flash | IRAM |
| --- | ---: | ---: |
| FFT 正变换 | 3,046 µs | **3,235 µs** |
| cycles/蝶形 | 105 | **112** |

**放进去反而慢 6%。取指不是瓶颈。**

### 四条循环，IPC 全在 0.1–0.33

| 循环 | cycles | 指令数（约） | IPC |
| --- | ---: | ---: | ---: |
| 参照 FIR | 12 /MAC | 4 | 0.33 |
| 卷积 | 31.6 /MAC | 5 | 0.16 |
| 系数更新（逐样本） | 119 /MAC | 12 | 0.10 |
| **FFT 蝶形** | **105.8** | **10** | **0.09** |

FFT 蝶形是这批里**最干净的一段代码**——没有钳位、没有 `&mut self`、没有 64 位累加器链——**IPC 最低**。取指否了、双核否了，剩下的只能是内存系统本身。

`[据称]` 是 flash 控制器、缺数据缓存、还是乘法未流水，未测。

### 延迟搜索：栅格抽稀不行，但它是最后的固定成本

`[实测]` 一次搜索约 **32 ms**，每 256 ms 一次（`REFRESH_SAMPLES = 4096`），摊到每 tick **3.0 ms**——L=16 那 9,680 µs 的 31%。**而且它单独就能撑爆 30 ms 的 `MAX_SINGLE_HOLD_MS` 上界。**

最直接的想法是把延迟栅格每 4 个样本取一个（搜索成本 ÷4）。**试了，不行。**测出来这个模块自己的参考信号上：

| 真实延迟 | 网格上的最高分 |
| --- | ---: |
| 0 | lag 0，**1000** |
| 1 | lag −48，**146** |
| 7 | lag 56，**101** |

延迟为 1 时，**连相邻的 lag 0 和 lag 4 都相关不到**。宽带参考下**相关峰只有一个样本宽**，栅格一个都不能少。所以「只损失几个抽头余量」这个判断是错的。

剩下的两个旋钮是 `SEARCH`（找得到的延迟范围）和 `WINDOW`（能锁住的基频结构）——**两个都要拿能力换时间**，不是白捡的。`delay.rs` 里留了 `LAG_STEP = 1` 和一条 `const _: () = assert!`，让下一个想抽稀的人必须先删掉一句写着为什么不能的声明。

### 时钟：80 → 240 MHz，控制台没坏

`CpuClock` 的默认臂是 `_80MHz`，整块板一直跑在数据手册上限的三分之一。esp-hal 对 160/240 预设有一条注释说换 PLL 会影响 USB Serial/JTAG，而本仓库控制台正是它——**`[据称]`，一直没测。**

`[实测]` **测了，240 MHz 跑通，USB Serial/JTAG 控制台全程正常。**（只测过一次，这是它唯一的后续风险。）

| | @80 MHz | @240 MHz |
| --- | ---: | ---: |
| L=16 整体 | 9,735 µs | **3,248 µs** |
| **L=16 最坏 tick** | **39,594 µs（破 30 ms 界）** | **13,287 µs** |
| **延迟搜索最坏** | **32,870 µs（单独就破界）** | **10,957 µs** |
| L=32 / L=64 / L=128 整体 | 13,528 / 20,448 / 34,911 | 4,511 / 6,818 / **11,639** |
| L=128 最坏 tick | — | **21,614 µs**（30 ms 界内） |
| FFT / 参照 FIR | 3,235 / 34,629 µs | 1,079 / 11,549 µs |
| **cycles/蝶形** | 112 | **112（一点没变）** |
| **参照 FIR cycles/MAC** | 12 | **12（一点没变）** |

两件事同时成立：**最坏 tick 的问题自己消失了**（延迟搜索从 32.9 ms 到 11.0 ms，单独就在界内），**而 cycles 一个都没变**——时钟纯粹是个除数。

所以 `chip_init_at(CpuClock)` 加到了 `iot-chip-esp`，探针用一个常量在两者间切换，**两张表来自同一棵源码树、只差这一个常量。**

### 数据缓存：走不通，但原因不是「没开」

ESPHome 在 ESP32-S3 上跑 AEC 的 sdkconfig 里是：

```
CONFIG_ESP32S3_DEFAULT_CPU_FREQ_240: "y"
CONFIG_ESP32S3_DATA_CACHE_64KB: "y"
CONFIG_ESP32S3_DATA_CACHE_LINE_64B: "y"
```

后两条与 ESP-SR 那张 AEC 性能表的脚注**逐字相同**，而 ESP-SR 没有它们**直接拒绝启动**（`E (4) SR_SYS: Data cache should be 64KB`）。数据手册 3.1.5：数据缓存 32 KB（单 bank）或 **64 KB（双 bank）**。

**但这条路我走不通**：esp-hal 1.2 没有 S3 的缓存配置 API，esp-metadata 也没暴露对应的 eFuse 字段。**ESP-SR 的做法是「拒绝启动」而不是「去配它」，本身就说明这个大小是芯片启动时的属性，软件改不了。**

而且 IPC 那个谜题**不靠它解释**。四条循环按读写而非工作集大小排开：

| 循环 | 工作集 | 读写 | cycles |
| --- | ---: | --- | ---: |
| 参照 FIR | 5.2 KB | **只读** | 12 |
| 卷积 | 450 B | **只读** | 31.6 |
| FFT 蝶形 | 6 KB | **读+写** | 105.8 |
| 系数更新 | 450 B | **读+写** | 119 |

**工作集最小的那个不是最快的，只读的比读写的快。**S3 的数据缓存是 write-back，一个每样本每抽头都回写同一位置的内层循环是写回缓存最差的模式——这也顺带解释了 stride 4 为什么直接省下 76%：写次数除以 4。

`[据称]` 这块板有没有 64 KB 数据缓存，未读出来。**但提时钟之后它不再决定 AEC 塞不塞得下**——cycles 没变，只是墙钟除以了 3。

### 还有一条：这个 target 的 FPU 是关的

`[实测]` 探针里同形状的 f32 参照循环跑 **>120 秒**，而 i32 孪生 140 ms；二进制里带着 libgcc 的全部软浮点助手（`__mulsf3`、`__addsf3`…）。**浮点在 `xtensa-esp32s3-none-elf` 上走软件模拟。**

所以 ESP-DSP 那个 1.69 cycles/MAC 在这里够不着，「换成浮点」不是条捷径。已把 f32 参照从探针里撤掉（否则每次探针运行要多花两分钟），结论留在这里。

## 计时器本身：一次被折叠的标定，和一个最终没交付的数

`[测试]` 探针最初的版本报 cycles/MAC，为此加过时钟标定。**三版都被否决：**

1. `acc += 1` 链被强度削减成 `acc += 64`，读出 **85 GHz**。
2. `acc = acc * M + C`（LCG）正是 InstCombine 的 **pop idiom** 识别的形式，同样被折叠，读出 **251 MHz**。
3. 链内加 `black_box` 不折叠了，但每个 `black_box` 自身 ~100 周期，读出 **2.34 MHz**。

**最终 cycles/MAC 的软件标定被删掉了。** esp-hal 在这个目标上没有暴露循环计数器，而我写的每一种标定要么被折叠、要么被自己的屏障成本主导。

**它的替代品是现在这条参照循环**，而且比标定强得多：它不猜时钟，它**在同一个镜像里、同一块板上、同一套构建下**跑一条已知的活，然后把比值拿回来。时钟本身则直接用 `esp_hal::clock::cpu_clock()` 读回。

微秒是可靠的：systimer 跑在 XTAL（40 MHz × 0.4 = 16 MHz，`ticks >> 4`），与 CPU 时钟无关，所以 `Instant` 给出的是真实微秒，而日志墙钟与它一致。

## 文献对齐：三条路线被证据否掉，一条按计划改的东西也不该改

这一节记的是**查了外部资料之后决定不做的事**，以及为什么。

### 比例型 NLMS（PNLMS / IPNLMS）：否

最顺手的重构方向——按抽头大小分配步长。原始文献 Duttweiler 2000，以及综述对适用面的定性：

> PNLMS 的真正收益在回声路径**稀疏**时出现……主要应用是**线路/网络回声消除器**，因为混合电路的典型回声路径是稀疏的。**否则，对于弥散回声路径（典型就是在声学环境中观测到的），几乎没有任何收益。**

这块板就是声学环境。抄过来兑现不了。

### 子集轮转的部分更新：否，而且是降级

本来打算把「每 4 样本全量更新」换成「每样本更新 1/4 抽头、轮转」——乘加数完全一样，听起来严格更好。Partial Update LMS 那篇正好对比了这两者：

> **每 P 次迭代做一次更新，得到的滤波器与每步做 P 次更新完全相同。因此该算法在收敛性上毫无损失。**

子集版反而**有**损失，代价是把步长从 0.004 压到 0.001 才能追平。**当前实现已经是两者中更好的那个**，不用动。

### 混合式开环/闭环双讲检测：改了，然后撤掉

文献（IRISA；Benesty 等 2000）把双讲检测分成开环（麦克风×远端激励，与滤波器无关，收敛前可用）和闭环（麦克风×滤波器估计，收敛后最锐、收敛前无效），并建议**先用开环直到足够收敛，再切闭环**。当前实现两个都不是：它算的是 `残差 × 参考`，而残差 = mic − ŷ，已经含滤波器状态。

于是把三种统计量都实现了，在同一条房间路径上逐样本对比。结果：

| 说话人峰值 | 误冻结 | 冻结延迟 | 漏检 | 残余均方 | 过 `LEAKAGE_FREEZE` |
|---|---:|---:|---:|---:|---|
| 8000 | 0 | 752 | 751 | 26 038 827 | ✓ |
| 4000 | 0 | 0 | 32 000 | 7 366 231 | ✗ 差 43% |
| 2000 | 0 | 0 | 32 000 | 1 841 437 | ✗ 差 89% |
| 1000 | 0 | 0 | 32 000 | 460 200 | ✗ |
| 500 | 0 | 0 | 32 000 | 114 877 | ✗ |

**三个统计量在每一个电平上逐位相同。** 绑定约束是 `loud` 那个电平门，不是相关性：门限 `LEAKAGE_FREEZE = 1<<24` 是均方（RMS 4096 LSB），说话人峰值 4000 时残余均方只有 7 366 231，**低于门限 43%**，相关性根本没被读到。

所以混合式检测在这个电平设定下**买不到任何东西**。已撤回，`update` 保持两参数。留下的不是机制而是**一条钉住的盲区**：`gate.rs` 里 `a_talker_below_the_level_gate_is_not_detected` 断言 2000 LSB 说话人现在测出来低于门限、闸门不动；改门限是一次有意的动作，不是副作用。

这也说明真正要修的是门限，而门限标着 `[据称]`——它是照 `audio.md` 的麦克风标定推出来的，不是台架上量出来的。

### 双滤波器 Bi-LMSM：暂缓

Gänsler 2000 指出它不像 PNLMS 那样依赖稀疏假设，是声学场景对口的。但要两组系数加逐样本择优，乘加翻倍。本板稳态 ERLE 61.0 dB 对 G.168 的 15 dB 门槛，**没有需要它解决的问题**。

### 频域 / 多延时滤波器：维持否决

写完了 512 点定点 FFT，量出来每 tick 3,046 µs = 10 ms 预算的 182%，代码已删。文献侧不推翻这个决定。

## 内存核算曾是一个谎

`state_bytes()` 的注释写着「板子想提前知道占用多少时不必来问」。它数的是 `ring + taps`，**只覆盖了滤波器**：

| | 旧函数报的 | 板上实测 | host 实测 | 低报 |
|---|---:|---:|---:|---:|
| L=16 | 450 B | **2 592 B** | 2 616 B | 5.8× |
| L=128 | 898 B | **3 040 B** | 3 064 B | 3.4× |

板上比 host 少 24 B：`size_of` 跟着目标字长走，xtensa 的 `usize` 是 4 字节。**引用这个数必须说清在哪个目标上量的**——host 的数字不是这块板的代价。探针会打印当前目标的真值。

漏掉的是 `DelayEstimator` 的 **2 096 B**（两个 `[i16; 512]` 历史缓冲）。而 `nlms.rs` 里那条 `assert!(state_bytes(MAX_TAPS) < 1024, "a kilobyte was budgeted")` **就建立在这个数上，通过了**。探针至今在打 `[ECHO] --- L=16, 450 B of state ---`。

两条测试让它活下来，因为它们断言的正是错误函数的定义：

```rust
assert_eq!(bytes, ring + taps, "the estimate counts something twice");  // 恒真
assert!(bytes < 1024, ...);                                             // 在谎上通过
```

现在 `state_bytes<L>()` 就是 `size_of::<Canceller<L>>()`，L 是 const 泛型而不是运行时参数——**运行时参数让调用方能传一个编译器无法核对的数字，那正是它漂移的原因**。新增的 `the_reported_size_covers_the_whole_canceller_not_just_the_filter` 会断言报告值至少装得下滤波器和延迟估计器两个主要部分。

## 未决与边界

- **CPU 过了，而且是全线。** `@80 MHz` + 分块自适应之后 L=16 是 9,680 µs；**再提到 240 MHz，L=16 是 3,248 µs、L=128 是 11,639 µs，最坏 tick 21.6 ms，全部落在 30 ms 界内。** USB Serial/JTAG 控制台实测没坏。代价是收敛变慢（whole-file 20.9 → 16.2 dB），稳态 ERLE 逐位不变。 `aec/mod.rs` 与 44 个单元测试、`tests/aec_erle.rs` 全部留在树里，作为「这条路走不通」的证据与算法正确性的证明；`aec-probe` 留在 `check-s3` 的 bin 列表里，成本一变就编译失败。
- **时钟已改成 240 MHz，但只在探针里。** `chip_init_at(CpuClock)` 加在 `iot-chip-esp`，**产品固件仍走 `chip_init()` 的 80 MHz。** 换过去是一次全固件改动：功耗、PLL、USB Serial/JTAG 的长期稳定性（实测过一次，不是长期结论）。
- **这块板有没有 64 KB 数据缓存，未读出来。** esp-hal 无 API、esp-metadata 无 eFuse 字段，而 ESP-SR 没有它会拒绝启动。提时钟后它不再决定 AEC 塞不塞得下，但 IPC 那个谜题还在。
- **系数更新的 119 cycles/MAC 没解释。** 降频绕开了它，根子还在。取指已否（IRAM 反而慢 6%）、双核已否（两核数字逐位相同），剩下的只能是内存系统本身。`[据称]` 是 flash 控制器、缺数据缓存、还是乘法未流水，未测。
- **起始那半秒的冻结缺陷未修。** 冻结止住了损伤增长，止不住第一段，根因是相干度计量器 ~512 样本的滞后。
- **`[据称]` `LEAKAGE_FREEZE` 与 `MAX_COHERENCE` 未在本板标定**，仍取自 `audio.md` 的麦克风标定。
- **RAM 板上实测 3,040 B**（`state_bytes::<128>()`，L=16 是 2,592 B），预算 4 KB。host 上是 3,064 B。
- **`state_bytes()` 曾低报 3.4–5.8 倍**，现已按整个 `Canceller` 计量，见本文件《内存核算曾是一个谎》一节。
- **参考源尚未接入**：数字抽头取自 `audio_out::render_slice`；`Speaker` 没有 `played_frames()`。
- **PSRAM 仍未开启**（按约定先量后开），3 KB 不需要它。
- **LTO 现在是整个 workspace 的 release 默认**（`apps/iot/Cargo.toml`）。它让 AEC 快 9.6%，代价是探针的计时括号会被优化掉，所以 `AdaptiveFilter::process` 带 `#[inline(never)]`。这个属性是给测量用的，不是给性能用的——谁去掉它，下一份 CPU 数字就是假的。
- **固定地板未攻。** L=16 的 9,680 µs 里滤波器只占 3,945，其余是延迟搜索 3,059 + 计量器 1,839 + 未归因 2,731。
- **延迟搜索不再破界**（240 MHz 下最坏 11.0 ms），但栅格抽稀已否（宽带参考下相关峰只有一个样本宽）。`SEARCH` 和 `WINDOW` 两个旋钮仍要拿能力换时间。
- **NLR/残差抑制未实现**，测得的 ERLE 是它之前的值。
- **真实回声路径仍未验证。** 没有公开录音有，G.168 也说声学向量「for further study」。只剩自己录这一条路，而那需要一个能同时放音与采集的构建。
