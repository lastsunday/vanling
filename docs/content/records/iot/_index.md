# IoT 实现记录

Vanling 自有 ESP32 固件（`apps/iot`）的实现判断记录。**AI 产出，未经人类审阅**，见[上级说明](@/records/_index.md)。

对应的系统说明在[开发文档 / IoT 固件](@/development/iot/_index.md)。

## 发现速查

**下面这张表是回答「某个结论是什么、凭多少数字」的地方。绝大多数问题到这一层就结束，不必读全文。** 依据标注沿用各记录正文的约定：结论 + 仍然生效的数字 + 被否方案及原因 + 未决项。

### 摄像头（GC2145 + ST7789）

| 发现 | 结论 | 数字 |
| --- | --- | --- |
| 视野怎么算 | **输出宽 ÷ 阵列宽，与寄存器取值无关**。ratio 5 整除，320×240 就是满视野 | 320/1600 = 1/5 |
| bins 与帧率 | 同一个开关的两面。本仓库写 `0x00` | `0x00` 4.5 fps / 691 KB/s；`0x01` 10 fps / 1558 KB/s |
| ratio 档位 | ratio 5 是唯一读满整个阵列的档；1 不出帧，3/4 欠采样 | ratio 3 = 3444 KB/s，ratio 1 = 0 帧 |
| 标量模式 `0xfd` | 帧率翻倍但视野**更窄**，本驱动不写（留上电表 `0x00`）但读回 | 5 → 10 fps |
| 环形描述符链 | **已撤回，保留线性链**。外设不走完第一圈就停 | ring 28 KB/s vs 线性 645 KB/s |
| 线性链丢字节 | ring 必须整帧大小，代价是重建降到每秒 4 次 | 丢 1 字节后每行错开一行（移动条带） |
| PSRAM ring | **永远写乱**。esp-hal 无法表达 `internal SRAM only`，只能停在官方拒绝的配置上 | 150 KB ring |
| 帧率上限 | 来自数据量，**不是** AEC 曝光。想更快只能缩窗口或换芯片 | 5.2 fps；exposure 486 lines vs 读出 ~1200 |
| 像素时钟 | 固定 24 MHz。改 20 MHz 时 PLL 不锁，输出**结构对、全是噪声**且寄存器读回一切正常 | — |
| 反复进出 Camera 页 | 链每次重建且建起来就堵。render 侧 8% → 29–36% | 启动直入 11 repaints/窗口；反复进出 25–29 |
| 进页空窗 | 约 192 ms 无法缩短，用过渡帧 `CAMERA WAIT` 缓解 | 5.2 fps ⇒ ~192 ms |
| 面板读回 | **面板没有 MISO**，寄存器读回全是 `0x00`，只能目视验证 | — |
| 帧缓冲持有者 | `FrameOwner` 三变体，第四种组合不可表示（曾用两个标志导致永久卡死） | 153,600 B |

### 音频（ES7210 + ZTS6216）

| 发现 | 结论 | 数字 |
| --- | --- | --- |
| 采集平面可否节流 | **不可**。环只有 `sample()` 排空，被批到 30 s 就是环撞满 + I2S 停机 | ring 60 ms 撞满 |
| `Off` 的实现 | 必须在消费端主动 park 链，不能只是不 poll | 需求生效后 1 ms 停链 |
| 静音判定 | 必须读作「没变化」，否则整条 diff 链空转 | — |
| 平面边际代价 | **随别的任务醒着而变，不是常数** | 12.52%（独自跑）→ 15.73%（有旁侧） |
| 节流的效果 | 不省设备总量，只是把执行器从一处搬到另一处 | 94.8% → 94.0% |
| poll 侧缩放 | 按实际节奏缩放，两端都与实测对上 | +0.6% / −4.1%（缩放前高 40%） |
| 量化噪声 | 会喂出 **65 dBA 的假底噪**，dBA 表需对原始表换算 | 65 dBA |
| SPL 标定 | `0 dBFS = 102 dB SPL` 是这一颗麦克风的值（397.8 mV/Pa → 满量程 2.51 Pa） | 101.98 dB |

### 运动（QMI8658A）

| 发现 | 结论 | 数字 |
| --- | --- | --- |
| tap engine | **不可用**（据称），敲击判定改在 core 侧；`QMI8658_CAPABILITIES` 不声明 `TAP` | — |
| 敲击门限 | 用**原始幅值**，不减重力估计 | 静止摆动 8–22 mG；门限 150 mG / 峰值 250 mG |
| aLPF 滤波器 | **实测无关，关掉**。敲击是宽带瞬态，滤波只会削峰 | 静止噪声与敲击读数完全一致 |
| No-Motion | 是**电平不是事件**，只发布 0→1 上升沿，否则静止时按帧率持续报 `Still` | — |
| 摇晃判据 | 比较矢量残差并数**过零次数**，不是门限之上的时间 | 2.0 g；W3C 的 2.5 g/60 Hz 单轴幅值不适用 |

### 输入与触摸

| 发现 | 结论 | 数字 |
| --- | --- | --- |
| 页面循环 | 硬件上正确。**`[DISPLAY]` 的 2 秒窗口看不出页序**，据此判断过一次「页面在乱跳」是错的 | 46 次跃迁，偏离 0、重复 0 |
| 四路轮询 | 只有 capture 可关；交互路径按设计不可关 | 稳定形态 `button 0 / touch 1 / motion 3 / capture 16–20 ms` |
| 交互地板 | 与需求无关的理论下限，不是调优空间 | 10.87% |

### 硬件约束

| 发现 | 结论 | 数字 |
| --- | --- | --- |
| 电源管理 | **还没有 PM，所以没有时钟源锁是对的**（加两把无持有者的锁就是死代码）。但顺序不能反 | — |
| light-sleep | 外设被时钟门控且不产生中断，依赖外设中断的驱动必须持 `NO_LIGHT_SLEEP` | DVP 与 I2S 链都在此列 |
| 共用 MCLK | 两个单元跑在各自时钟域，**发送单元驱动引脚、采集被强制从属**，方向不可交换 | `with_signal_loopback` 名字是唯一误导处 |
| 主任务栈 | 随摄像头进产品而变，以链接 ELF 符号为准 | `_stack_start_cpu0` = 83,060 B |
| esp-hal 栈溢出 watchpoint | 会误触发，不能当溢出判据 | — |

## 探针

**每个探针是独立 bin，把框架里的一层单独接到真硬件上。改驱动之前先看这里——「哪个问题跑哪个探针」在这一层就该结束。**

它们不是产品的另一种形态：产品固件**产生不出**探针能产生的那些输入。整机五页四平面全是 `Continuous`，所以产品上永远拿不到 `(配置 × 节奏)` 矩阵里除默认格以外的任何一格。

| 探针 | 回答什么 | 报什么数 |
| --- | --- | --- |
| `demand-probe` | 运动平面每格配置 × 节奏，各值多少 | 每格先 settle 再测：总线事务/秒、执行器占用墙钟占比、测量的 poll 数（供前两者互相校验） |
| `camera-probe` | 相机取到帧、面板逐像素写出，画面有没有被替换 | 帧字节数与校验；「画面看着不对」不是测量 |
| `audio-probe` | 放音链路独占运行时的稳态 | 交替两个音效的 stall 与缺口 |
| `multicore-s3` | 启动第二核能否在主栈底下存活 | 栈顶是否被启动序例覆写（`ThreadFlag` 就住在那里） |

```sh
moon run iot:probe-demand-s3 && moon run iot:flash-probe-demand-s3
```

`probe-*-s3` 只构建，`flash-probe-*-s3` 才烧录；端口在 `moon.yml` 的命令里。

**四个 bin 每次 `check-s3` 都编一遍，只编不链。** 没有编译它们的探针会烂在原地：每个都自己调一遍 bring-up 或芯片 API，`Board`、`Speaker`、芯片层一改就会编译失败，而没人会注意到，直到某天在台架上要用。

**探针与产品的分界线会无声地被挪动**：两边各自都还能编译，所以编译期抓不到漂移。改动若触及探针调用的框架路径（`poll_plan_of`、`MotionConfig::for_mode`、驱动入口），把探针烧一次当作证据，不要只等编译通过。
