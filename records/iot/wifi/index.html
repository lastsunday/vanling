Wi-Fi 实现记录

apps/iot 的 Wi-Fi 链路：从「扫到哪些网络」到「拿到一个地址」。AI 产出，未经人类审阅，见上级说明。

每条判断标注依据：[测试] 有对应单元测试，[实测] 有硬件测量并附复现方式，[据称] 未复现、仅留痕。

状态

两颗芯片的探针都在台架上跑完（扫描 + 关联 + DHCP）。产品页分两片：只读的那一片已落地（DisplayPage::Network：阶段 + 当前 AP + 地址 + 扫描列表），第二片也落了盘（4×4 键盘、回显键、逐行滑动的列表、列表迟滞与缓存、选中行反色、开放网络、失败分档、扫描门控与退避，以及工具条：有链路时一个 LEAVE 按钮、无链路时一个 SCAN 按钮，前者执行前问一次、后者不问 —— 见「产品页」），凭据已落盘（creds 分区 + 自控槽格式，开机自己读回来、关联成功即写，见「凭据落在哪」），已存网络在列表里画 *、长按那一行 = 忘记，点一下已存的那一行就用设备自己存的那份口令去连（见「点已存的一行就用库里的口令」）。后四轮报来的缺陷与两处结构修正还在这份记录里。面板这条路有一条不需要手指的验法：IOT_PANEL_BENCH 构建开机后按面板自己的坐标把口令打一遍，再按工具条与确认框的坐标走完断开、点回那一行、断开、忘记、点回那一行、取消与重扫（见「按面板路径打字」与后四轮的读数）；它证明的是状态机与几何，而触摸手感与纯黑/背光仍要人点一次面板才算验过（板上只有 FT6336 产面板坐标，软件合成不了触摸）。状态层另有一层可达状态穷举（35 个动作、8,800 个状态、四条不变量，见「离开后点回那一行、以及一次丢掉的列表修正」）。没有面板的板子也有了一扇前门：iot-core::provision 是协议（45 条宿主机测试），iot-app::provision 把它接在「开放 AP + DHCP + 全答 DNS + 配置页」上，与面板那扇门在 configure 里 select 竞争（见「没有面板的板子怎么配网」）；面板那条路一点没动。这一扇门两块板都已在台架上跑通（C6 全链路、S3 修掉三处之后，见「台架：从链接到手机，再到四轮修正」）。回到设置模式的入口之一是启动页：两块板开机先画 1.5 s，按住 BOOT 才进设置模式，落 network 页；启动页这 1.5 s 里一条链路都不建（见「回到设置模式：启动页上按住 BOOT」）。没有凭据 = 离线设备：不自动进设置模式、不广播 AP，面板页只在有人看时扫描（页上保留 SCAN | AP 两格，按 AP 才起接入点，有屏板这一档默认带口令）；存盘网络带 BSSID/信道提示，下次开机直接去那个信道（fast_connect）。配置页已有第三版：首屏列表内嵌、图标内联、一次刷新只开一条连接、只有按钮才唤醒扫描，语言切换在页头、密码走底部弹窗、每行带 BSSID（见「刷新七八次就白屏」）；面板的列表行也在同一天补上了该网络自己的 BSSID（名字下一行，见同节）。未完成的事在文末；其余都在下面。

内存：三个决定（S3 上的账）

这一节讲 S3 的三个决定；C6 的对应选择在下面那一节。

驱动的堆：两块内部 DRAM，一块 32 KiB reclaimed + 一块 16 KiB dram_seg

[实测] esp-radio 是闭源 blob，通过 malloc 分配，所以符号必须在最终镜像里，esp-alloc 提供它们，而这个模块是背后的内存。

  • reclaimed 区（0x3FCF0000 以上）是二段 bootloader 留给 flash cache 的 DRAM，esp-hal 的链接脚本把它留给堆。但它的大小 = 64 KiB − 数据缓存，默认 64 KiB 缓存时这段是空的（本仓既有 ELF 在 0x3FCF0000 以上没有任何符号）。scripts/iot-xtensa.sh 把缓存压到 32KB，换来 32 KiB。
  • dram_seg 里那一半（先是 32 KiB，2026-10-16 收到 16 KiB）只有在 app 自己的堆搬去 PSRAM 之后才付得起（见下条）：那一步把主栈从 63,788 B 抬到 125,788 B，而实测峰值 39,809 B。这次收到 16 KiB 是另一条账：blob 的 IRAM 代码要在 dram_seg 里留一份同样大的镜像（31,980 B），加上产品自己的静态量之后静态量越过 RWDATA、主栈位置只剩 53,272 B（短断言 12,264 B），链接直接失败 —— 见「同一套代码，两颗芯片」里的驱动堆那一节。

两块都标 MemoryCapability::Internal：驱动的 pbuf 池要走 MAC 的 DMA，那条路到不了 PSRAM。

ESP_HAL_CONFIG_DATA_CACHE_SIZE 不能进 .cargo/config.toml：esp-config 把「对本芯片不生效的选项」当未知选项直接失败，而这个选项只在 S2/S3 生效，会把 C6 的构建炸掉。所以它放在 iot-xtensa.sh 里，并且按 --target 判定（无条件 export 时 moon run iot:check-c6 直接死在 esp-config 上）。

代价：面板与相机 DMA 在没有一半数据缓存的情况下跑。面板整帧是 DMA 写、渲染路径自己的工作集在内部 DRAM，所以量过的那几条路径不读它 —— 但这是预期不是实测，[INPUT] 的 17–25 ms 最坏 tick 与 AEC 那些数字需要重测。

app 的堆：搬进 PSRAM，因为没有第三处（S3）

[实测] 产品要装下 Wi-Fi，64 KiB 的 Rust 堆必须离开 dram_seg，而剩下的两处是：动相机那 150 KiB arena（已经在售的页面，要人点头），或者用板上那 8 MB octal PSRAM。chip_init_at 顺带把 PSRAM 映射好（Psram::new(PSRAM::steal(), PsramConfig::default())；那个 peripheral 是 Peripherals 的一个字段，直接取走是 partial move、函数返回不了整个结构体，steal() 拿到的是同一个 handle），app 的 main 再把堆指过去。

映射完必须自己验：写一个步长为 7 的图案再读回，两端各 4 KiB。esp-hal 只保证它把窗口映射出来，不保证这个 build 的 SPI 时序对，而 PSRAM 时序错了不 panic，是「十分钟后随机崩」。所以三种结果分开报：没有窗口 / 有窗口但读不回 / 可用，产品在第二种报错复位。台架实测：Ready(len: 8388608)。

PsramConfig::default() 不填 core clock：S3 的 SPI0/SPI1 挂在 APB 上，而 [set_cpu_clock] 只动 CPU 不动 APB，所以 CPU 频率不是 SPI 的源时钟，钉一个 core clock 就是拿一个不是源的时钟去除。

wifi_force_pd：补上 esp-radio 没人调的 init()（S3）

[实测] esp-radio 1.0.0-beta.1 里有一个 pub(crate) fn init()，负责开 modem 时钟、给 WiFi 域上电、脉冲复位、取 RTC 唤醒锁 —— 全 crate 没有任何调用者。本板实测停在 ROM 的 APB_CTRL.wifi_clk_en = 0xfffce030 与 dig_pwc bit 17（wifi_force_pd）= 1。chip-esp::ungate_radio() 现在代做这几条写（上游 init_clocks 与 enable_wifi_power_domain 的 S3 臂），探针在 take_wifi() 之前调用，实测 0xfffce030 → 0xffffdfdf、0x20000 → 0。

它没有让扫描变稳（改前 0/0/1，改后 0/1/1/1/1/1 与 1/1/0/1/0/1），所以射频的电源/时钟状态不是扫描抖动的成因。保留是因为谁也不该让驱动跑在上电状态没人设的射频上，不是因为它解决了什么。

同一套代码，两颗芯片

[实测] 探针与产品用的是同一份源码，两颗芯片各自构建各自烧录。差异全部落在 iot-chip-esp 之下，调用方看到的是一个入口：

iot_chip_esp::init_heap(&HEAP, HEAP_BYTES);   // 堆从哪来：这一句不问
iot_chip_esp::ungate_radio();                // 射频上电：这一句不问
let station = board.take_wifi();             // 射频是哪个 part 的：这一句不问

具体地，take_wifi() 的实现在两块板的板模块里各写一份（板层按构造就知道自己是谁），而 esp-radio 的 blob 由板特征选：lckfb-szpi-esp32s3 带 esp-radio/esp32s3、esp32c6-devkitc-1 带 esp-radio/esp32c6。esp-alloc 的芯片特征同理，从 radio 这个组件 feature 里挪到了芯片 feature 上（esp-alloc?/<chip>），因为「哪个 part 在编译」只有芯片 feature 知道；scripts/iot-feature-check.sh 现在把这套组合在两颗芯片上各编译一遍。

通用堆：S3 拿 PSRAM，C6 拿一块静态量

[实测] C6 没有 PSRAM（esp-hal 的 psram 模块按 soc_has_psram 编译，C6 不在其中），所以「app 的堆放 PSRAM」这条只在 S3 上成立。C6 的做法是芯片层里一块 64 KiB 的 dram_seg 静态量 —— 与产品入口原先自己声明的那块是同一块内存、同一节，搬进芯片层只是因为谁提供内存是 part 的事实，不是入口点该知道的事。两个 arm 的差别只在内存从哪来，HeapSource 只出现在日志里。

[实测] 入口点现在只有一句 init_heap，它同时管三件以前散在调用方的事：窗口从哪来、bytes 是否超出这块 part 能给的、要不到窗口时复位并留下原因（"this module has no PSRAM to map" / "PSRAM mapped and did not read back"，后者附上映射的大小 —— 那个数只在 init_psram 里还看得到，所以日志留在那里）。

驱动的堆：S3 两块，C6 一块

[实测] 两颗芯片现在是同一个总数 49,152 B（48 KiB）、不同的分法：C6 只有 dram_seg 一块 48 KiB，S3 是 32 KiB reclaimed + 16 KiB dram_seg。上板日志一行就是这两块：[WIFI] driver heap: 16384 B in dram_seg + 32768 B above it (dcache-reclaimed), both internal。

[实测] S3 的 dram_seg 那一半从 32 KiB 收到 16 KiB（2026-10-16），理由是上面那条账：blob 的 IRAM 代码要在 dram_seg 里留一份同样大的镜像（31,980 B），加上产品自己的静态量之后静态量越过 RWDATA 的末尾，主栈位置只剩 53,272 B（短断言 12,264 B），链接失败 —— 把常量改回 32 KiB 可以一行复现。收的是 dram_seg 那一半，不是 reclaimed 那半 —— 后者落在 0x3fcf0000，在 dram_seg 之外，本来就不占主栈。

收完的实测（链接期看符号，运行值看上板日志）：

四条约束决定了「48 KiB 分两块还是一块」：

  • #[ram(unstable(dcache_reclaimed))] 在 C6 上编不出来 —— 那个 procmacro feature 只由 esp-hal/esp32s3 打开（esp-hal/Cargo.toml 里它是 esp32s3 = [...] 的一行；esp32s2 也没开）。所以 reclaimed 那块是 S3 独有的，不是「忘了在 C6 上加」。
  • reclaimed 那块不占主栈，但不是白来的：它是二级 bootloader 的 flash cache 让出来的 DRAM，esp-hal 的链接脚本把它留给堆，代价是把数据缓存砍半（scripts/iot-xtensa.sh）—— 换掉的是缓存命中率。
  • C6 上没有第三个地方。它有 400 KiB 内部 DRAM；64 KiB 给 app 堆、48 KiB 给驱动堆之后，主栈实测 247,400 B（断言下限之上 181,864 B），其余是驱动的静态量。
  • 余量现在两边一样紧：C6 的驱动实测用掉 35,028 B（48 KiB 里余 28.7%），S3 用掉 33,332 B（48 KiB 里余 32.2%；用量是 10-15 那次在 64 KiB 预算下量的，预算本身今天上板量到）。调大 DYNAMIC_RX_BUFFERS 是两块板一起付账 —— 文档区间 47–57 KiB 的高端正是 6 个动态 buffer。

要把那 32 KiB 拿回来，唯一的路是把 blob 的 IRAM 代码送去 flash，本仓做不到。 esp-hal 的脚本里这件事得插在 .rotext_dummy 的预留和 rwtext.x 的归属规则之间，而两者在同一个生成文件里（ld/esp32s3/esp32s3.x），不在仓库手上。试过的做法（脚本排在 linkall.x 之前去抢那几段）链接是过的、镜像也是坏的：预留段永远落在 .text 之前，被送去 flash 的代码只能落在 IROM 原点 0x42000020，flash 偏移 0x20，和 .rodata 的头一页撞上 —— 段表里 paddr 就是它的 vaddr，两个段会写到同一片 flash。正路是给 esp-hal 加一个能容纳这件事的钩子（上游），不是本仓自己拼脚本。

扫描：一次不是测量，两次也是

[实测] 同一个镜像连刷三次，第一次扫描分别返回 0 / 0 / 1 个 AP。连扫 6 轮，两次开机：

开机 A:  0, 1, 1, 2, 2, 1 个
开机 B:  1, 1, 1, 2, 0, 0 个

结论只能是「单次扫描不是测量」：条数在同一次开机里就来回跳。附近最强的 AP 稳定在 −50 dBm，所以不是信号余量的问题。曾经写成过「第一次扫描永远是空的」，被开机 B 直接推翻（它第一次就有，而第 5、6 轮是空的）。

一轮扫描的节奏

产品只在扫描列表真的在屏上时才问射频（DisplayPage::Network，见「页面何时扫」）；只要在扫，节奏放在 iot-core::drivers::network（SURVEY_PAUSE_MS = 5_000、SURVEY_EMPTY_PAUSE_MS = 1_000、SURVEY_EMPTY_RETRIES = 3、空闲退避的 SURVEY_IDLE_PAUSE_MS = 15_000 / SURVEY_IDLE_MAX_PAUSE_MS = 30_000 / SURVEY_IDLE_ROUNDS = 3，判据是 survey_pause_after(empty_rounds, idle_rounds)），因为它和 MAX_LISTED_APS 一样是「怎么问射频」的政策，而不是循环的实现细节 —— 而且只有设备能跑到的路，必须由测试钉住。

规则三条：找到东西就歇满 5 s；空轮 1 s 后重试，但连续三个空轮之后就不再加急（第四个起按 5 s 的间隔）；连续三轮没人碰过面板就把间隔退到 15 s，再连续三次退到 30 s（idle_rounds 只被点击/滑动/换页清零）。后者是因为一个没人看的列表每 5.8 s 重扫一次，代价全在射频与主栈上，而屏幕上什么都没变。

[测试] 三条钉住它（a_survey_that_found_something_rests_the_whole_pause、an_empty_place_stops_being_retried_every_second、a_room_nobody_acts_on_is_read_less_and_less_often）。前两条是补的，因为上板先抓到了错：判据写成 *empty_rounds <= SURVEY_EMPTY_RETRIES 时，非空轮（计数为 0）也落进快重试那一支，日志立刻是每 1.8 s 一轮而不是 5.8 s。改完重刷，间隔回到 5.8 s，空轮那次重试在 1.76 s 后。

列表为什么不跳

[实测] 产品镜像 281 行的读数里，同一张列表在相邻两轮之间换过行序：每轮的条数 0 行 17 次 / 1 行 53 次 / 2 行 39 次 / 3 行 31 次 / 4–6 行 4 次，信道 11 的读数 σ≈3.1 dB（−81..−51）、信道 1 是 2.4、信道 6 是 2.1。而 rank_aps 本来就按信号从强到弱排 —— 所以「经常跳」不是排序错了，是每一轮都拿一次性的读数重排。

政策因此收进 core（SurveyHistory，core/src/drivers/network.rs），和 <n>-<m>/8 一样是「怎么读射频」而不是循环的实现细节：

页面何时扫

PagePlane（app/src/render.rs 的 PAGE）是页面状态的唯一共享读数：渲染循环每 pass 把 manager.state().page 发布进去，网络任务用 PAGE.wait_for_list() 等「列表在屏上」，并 select3 在「扫描间隔到」/「页面回到列表」/「staged 凭据就绪」之间醒。

放共享状态而不是加一条消息：页面是状态（幂等、只有最新值有意义），走 channel 就要一个深度 1 的队列、写者侧的变化检测、以及被拒发送时的重试 —— 三个只为绕开「状态被当消息送」而存在的机制。这与 EffectiveDemand 同一形状。

为什么门控在任务这里而不是让扫描自己判断：扫描是个死循环，它没有「页面」这个输入；把它接进来的是唯一能同时看到页面与射频的那一层。切页回来时 wait_for_list() 返回「等过」，所以退避计数被清零，进页立刻重扫一次。

[实测] 「回到列表」必须是边沿，不能是电平 —— 这是同一处第二次被上板推翻。第一版把 wait_for_list() 放在扫描间隔那一支的第三个分支上，而列表当时本来就在屏上：电平检查在第一次 poll 就满足，于是 5 s 的歇息被整段跳过。修好前一次 120 s 的读数：152 轮、相邻两轮相差 790 ms（survey found 的时间戳），退避一次都没生效 —— 也就是射频一直在扫，而屏幕上什么都没变。

修法是在 PagePlane 上加 wait_for_return()：先读当前页，再等它变化成列表页，于是「离开又回来」与「一直没离开」不再是一回事。它是边沿，wait_for_list() 是电平，两个都在用：前者给歇息当断路器，后者给循环问「现在该不该扫」。[测试] 一条钉住这个区别（a_rest_on_the_list_is_not_cut_short_by_the_list_being_up：同一个 plane 上，电平在列表上是 Ready，边沿是 Pending；先离开再回来才是 Ready）。

「已连接」= 关联 且 拿到地址，而地址要有人回说

[据称，来自参考固件] xiaozhi-esp32 的 WifiStation 里 WIFI_EVENT_STA_CONNECTED 的处理函数是空的，连接位是在 IP_EVENT_STA_GOT_IP 里置的。本仓库照这个口径：关联成功而没有地址的链路，产品在上面做不了任何事。

[实测] 带凭据跑起来才暴露：联上、拿到地址、40 秒报告全写 phase Connecting —— Connected 这个分支全仓没有任何一处赋值。地址归 embassy-net 的 stack 所有，而 Station trait 上只有 status()，拿到地址的那一层没有回说的接口。照这个接口做产品页，连上之后面板会一直显示「连接中」。

规则因此放进 core，成为可测的值而不是注释：LinkStatus::with_address(Option<Ipv4>)（有地址即 Connected；地址没了退回 Connecting；Failed 不被地址复活，三个 host 测试钉住）+ Station::note_address。调用点是每个报告窗口一次，不只是第一次 —— 租约失效只有那个循环看得见。改完再跑：phase Connected 稳 40 秒。

分区表

[实测] espflash 默认给 esp32s3 写 factory 1 MB，而本仓固件加 Wi-Fi 之前已经 630 KB。apps/iot/partitions/lckfb-szpi-esp32s3.csv 给 factory 6 MB，并带一个 4 KiB 的 phy_init。

phy_init 原本故意没写：esp-radio 的 Xtensa 构建把驱动的标定恢复钩子实现成 todo!()（ld/esp32s3_provides.x 把 misc_nvs_restore 绑到它，blob 里是未定义引用），而驱动看得见标定分区就会走那条路。[实测] 这条路走不到 —— 分区在场时 esp_wifi_init 不 panic，扫描正常。分区保留，它就是驱动第一次开机写下标定数据的地方。C6 那张也带 phy_init，同一个用途。

凭据落在哪（creds 分区）

esp-storage 0.10 + 自控槽格式，不引 NVS：NVS 是另一套带自己 KV 语义的 blob，而这一处要存的是一个定长列表，格式自己拿得住、能一行行读。

分区：两张板的表都加 creds,data,undefined,,0x2000,，紧跟 factory 之后，既有三条分区的偏移一格未动。[实测] 离线复验（espflash partition-table --to-binary <csv> -o pt.bin 再 --to-csv pt.bin）：S3 creds 落在 0x610000、C6 落在 0x110000，factory 仍是 0x10000。两个 4 KiB 槽（8 KiB）是双槽轮写要的：一次保存只写「上次没写的那一槽」，读的时候取 sequence 大的那条 —— 写到一半掉电留下的是另一条的旧副本，不是半条记录。子类型必须写名字（undefined = DATA_UNDEFINED 0x06）：写十六进制会让 esp-idf-part 在 unwrap() 上 panic（已在不烧板的前提下验过，见待办 5 的 ②）。

格式：core/src/drivers/credentials.rs。记录 = 12 B 头（magic VLNC + 版本 + 条数 + 体长）+ 每条 1 + 32 + 1 + 64 + 2 B + 4 B CRC，RECORD_BYTES = 1016，两条 const _: () = assert!(...) 钉住它装得进一个扇区；9 条宿主机测试钉住槽规则、「保存到一半丢电」与坏 CRC 的判读。

时机在哪为什么
开机读表、开库Board::new，在射频之前读表要一帧 3 KiB 的缓冲区，而在别的部件起来之前那段还拿得到；分区表读不出来或没有 creds 时只记一行日志并交 None（读不到就不保存，设备照常联网）
开机试哪条link：先构建输入，再已存列表的第一条（最近保存的那条），都没有才回落 setup已存那条被拒是 GiveBack 而不是 Retry：面板就在一次点击之外，那是这设备的另一个答案；退避重试是「只有这一条能试」的构建才有的行为
写hold：关联成功那一刻，每条凭据一次；只写构建时凭据与面板输入那份（Provenance::Named）写的是口令，而口令的答案在手上了；等 DHCP 会把「拿到地址」卡在「口令能不能用」和「下次开机还能不能用」之间。Refusal::Retry 的重试路径不会重复写（kept 闩住）。库自己交出来的那份不写（Provenance::Stored：开机自读的第一条、以及点已存行那一条）—— 那份副本就是盘上这一条，写回去只是白烧一个扇区，而开机那条本来就在最前；代价是点已存行连上不会把它顶到最前（remember 的置顶因此只发生在面板重新打了一次口令那种场合）
擦Store::forget：长按列表里已存的那一行、确认框答「忘记」那一刻，整条记录重写擦掉的是一条口令，不可逆 —— 要再连得从头打一遍，所以只有它问人；断开还能再连，代价小

写盘策略：S3 用 FlashStorage::multicore_auto_park()，C6 直接构造（单核）。本应用从不启动第二核，所以默认策略（另一核在跑就 Err）今天一样能写；选 auto-park 是为了以后真起第二核时不用回来想起这件事。

主栈的账（这是接线撞上的第四个问题，[实测]）：Store 值 ~1000 B（SavedNetworks 981 + 序号 + 槽号），而 serve/link/named_by_build/setup 都是同一个任务里的 async fn，每个按值携带它的帧都是主栈自己那一段的静态量（__embassy_main::POOL）。按值直传时 POOL 从 42,144 B 涨到 53,176 B，静态量越过 RWDATA 末尾 3,928 B，ld 报 stack.x:13 cannot move location counter backwards，主栈只剩 53,624 B（断言下限 65,536 B）。改成在板层装箱一次（Option<Box<CredentialStore>>，1 KB 落在 PSRAM 堆上）之后 POOL 只涨 976 B：[DISPLAY] main stack 65,944 B（bench 镜像）/ 66,168 B（产品镜像），对比 A 阶段的 67,704 / 68,600 B —— 这一整套功能净吃 ~1.8 KB，余量 408 B。这个余量就是下一次加静态量会撞到的墙，而撞到的是编译期断言，不是运行时的栈溢出。**再往后（工具条 + 掩码那一轮）**又吃掉一点，[实测] 链接期余量变成产品镜像 65,880 B（+344）、bench 镜像 65,560 B（+24）—— bench 那 320 B 差在它自己那批 log 的 Arguments 表落进 .data（render_loop 的 PanelBench 因此装箱，future 少 28 B 才重新过链接）。

面板分层那一轮（page::Part/page::walk + stamp::fill_surface）再量：产品镜像 +408 B（构建时给了网络的那一份）、bench 镜像 +88 B（docker run … espressif/idf-rust:esp32s3_1.95.0.0 里 nm … | grep _stack_，余量 = _stack_start − _stack_end − 65536）；不给网络、只带 IOT_BOOT_PAGE=network 的产品镜像（就是这一轮最后烧在板上那份）是 +376 B，两份差的 32 B 在编译进去的那几个字符串上。这一轮没有新的 static：两个镜像的具名静态量逐字节同名同尺寸（各 308,284 B，nm --size-sort --print-size 对齐后无差），新增的全是 .text（产品 +15,404 B、bench 更多）。两者那 320 B 的差还是上面那句里的无符号段（.data 开头到第一个具名符号之间：产品 9,168 B、bench 9,480 B）—— 所以两个镜像的余量不能互相比较代码，只能同一个镜像前后比。

特征与分层落点

wifi 是元件 feature（模块轴），在 iot-bsp-esp 里一个文件一个模块，门控只在 components/mod.rs 一处；两块板的板 feature 都聚合它（两块板都有射频焊在板上）。iot-core 零 cfg：能力经组合点注入（HasWifi）。components/wifi.rs 本身跨芯片可用 —— 它只拿 peripherals::WIFI 与驱动的类型，两颗芯片各编译过一遍。

Station 的方法用 RPITIT 返回 impl Future，不要 + Send：产品把这些 future 与 input/render/control/feed 一起 join 在同一个任务栈上，没有 spawn。（Speaker 需要 Send 是因为它的 feed 在独立的高优先级 executor 上。）

take_wifi() 不能在 Board::new 里做：驱动的启动需要调度器已经跑起来（esp_rtos::start() 在 app 的入口里），所以板子交出的是外设而不是 station。

iot-chip-esp 的两个芯片 feature 各带五个芯片 feature 转发（esp-hal / esp-rtos / esp-println / esp-backtrace / esp-bootloader-esp-idf），console 另是一条轴（console-auto / console-uart），app 转发过来。原因是那三个 crate 的 build script 各自要求「恰好一个芯片 feature」和一个 console，平时都由 app 顺手给，于是任何没有 app 在场的构建死在别人的 build script 上 —— iot-feature-check.sh 第一次真跑到 wifi 就抓到了。这就是 features.md 规则 5：用到的每一处都要自己写出来。

手势删减：延迟在分类器里，不在面板

[测试] 触摸现在只剩 Press / Tap（抬指即发） / Swipe / LongPress / Ghost（GestureEvent::DoubleTap 与 TripleTap 已从词汇表删除，TouchDiagnostics 里那两个计数一起去掉）。

延迟的根因是点击曾经被含在嘴里：旧的 TouchGestures 把一次短抬存进 chamber（PendingTap），只有在 DOUBLE_CLICK_WINDOW_MS = 400 的窗口过期那一次 tick 里才发布 —— 也就是每一次点击都要等最多 400 ms 才被看见，页面跟着晚 400 ms 反应。删掉触摸多击之后 Tap 在抬指那一次采样上发布；多击窗口只留给硬件按钮（切页唯一的入口是硬件三连击，那是真按钮，窗口照旧 400 ms）。

GestureEvent::Tap 带 at_ms（抬指时刻），位置改报按下沿（down_x/down_y）而不是抬指坐标：面板粗糙，抬指坐标会漂；键盘用 at_ms 判断 800 ms 内的第二击是「换候选」而不是「又一个字符」。TouchGestures 的队列同时从 2 槽放宽到 4 槽（一次采样最多产出「两个触点各一个手势 + 这一次运行的幽灵脉冲」），满了丢最旧的。

离开后点回那一行、以及一次丢掉的列表修正（[实测]，2026-10-17 第四轮）

两个缺陷：一个是报出来的黑屏，另一个是扫出来的丢更新 —— 后者不修的话，忘记过一个网络之后，那一行的 * 有时会一直留着。

  • 离开链路后点回那一行，页面下面全黑。pick_row 的「又点了同一行就留着草稿」判据原来只看 selected，而链路升起清草稿、不清那一行（见「相位语义」）：链路一落，那一行还是被选中的，再点它被读成「同一行」→ 不建草稿，却把 keyboard 置起 → 面板把键盘区画在空草稿上，键与工具条都不画，这一页再没有能点的东西（这就是「全黑」）。判据补上 entry.is_some()：没有草稿就没有草稿可留，而「链路丢下的草稿不回来」是故意的（它不会再被交出去），所以那一行再点开的是新的空草稿。看不见的那一半写进了文档：NetworkSetup::keyboard 与 pick_row 都声明了不变量 keyboard ⇒ entry.is_some()。
  • 忘记之后那一行的 * 有时不消失。SCAN 平面原来是容量 1 的 Channel，try_send 满了就 Err 丢掉，而丢的偏偏是新的那一条：一轮扫描先发一次列表，紧接着（同一毫秒内，忘记正是在这一轮自己的停顿里被执行的）网络任务把「库里已经没它了」重标一遍再发一次 —— 槽里还压着第一条时，第二条被丢掉。页面于是留着一个早就不存在的已存标记，而后面每一轮都不会再纠：SurveyHistory 已经把那条修正当成「页面正在显示的列表」，下一轮比对说「列表没变，不重画」。修法是把平面换成一个新值覆盖旧值的槽（Signal 装值 + 一个独立的唤醒信号；唤醒与值分开，因为渲染循环停泊在唤醒上，停泊不能把列表取走 —— take() 是下一趟开头的事）。

「下次自动发现这类缺陷」的机制这一轮一起落了：状态层原来只有散点测试，现在多一层可达状态穷举 —— state::tests::reachable::every_state_the_page_can_reach_keeps_its_invariants 从开机态出发，用 35 个「页面真收得到的动作」（alphabet() 里逐个列名：三行的点与长按、工具条、确认框两键、按钮三态、键盘七键、两次滑动、射频的七种相位与三种扫描、以及渲染循环把四个闩交给射频的那四下）做广度优先，落到 8,800 个状态（0.90 s，上限 SWEEP_CAP = 20_000，并且断言「没触顶」—— 触顶就等于这个测试在宣称一份它没有的覆盖），对每一个新落到的状态查四条不变量：

点已存的一行就用库里的口令（[实测]，2026-10-17 第五轮）

已存网络（画 * 的那一行）点一下 = 用设备自己存在 creds 里的那份口令去连，不再让人重打一遍。这一条把凭据那条路上的所有权分开：口令库只有网络任务一个所有者（SavedNetworks 从不进 DeviceState —— S3 静态内存墙下那 980 B 落不成值，见「凭据落在哪」），页面能说的是「哪个网络」而说不出「它的口令是什么」；于是页面点一下只交名字，答复（库里有没有、能不能连）由射频给。

  • 请求是同一个平面的两种形状。CredentialPlane/CREDENTIALS 改名 JoinPlane/JOIN，消息由 Credentials 变成 JoinRequest::{Typed(Credentials), Held(Ssid)} —— 同一个请求「帮多少忙」的两种，还是同一条单槽平面（不新开平面、不新加一条 select 臂）。DeviceState.credential 因此变成 DeviceState.join: Option<JoinRequest>（take_join()）：字段还是那一个，宽度只多一个判据字（Credentials 已是两个变体里宽的那个），没有新的 static。
  • 库里没有就回报页面。网络任务在两个读这条平面的地方（setup 的开头、以及链路已起时 hold 的窗口）都走同一个 asked_for()：Typed 直接用（Provenance::Named）；Held(name) 走 SavedNetworks::copy_of(name) 查库 —— 查到就用那份（Provenance::Stored），查不到就发 BusinessIntent::NoCopy(name)（走既有 INTENT_BUS，与 Link 报告同一条路）。页面收到后 no_copy()：只对当前选中的那一行成立（这期间点了别的行就是更新的问题，旧答复丢掉），升键盘问口令。
  • 被拒之后不落到死循环上。库那份也会被拒（对面改了口令）。那时 refused 照旧，而 reopen_entry 补一条选中的行没有草稿就造一个空的：键盘是拿草稿画的、工具条又被键盘藏起来，所以「有键盘、没草稿」是一页什么都点不到的东西 —— 而这一行偏偏只会被点第二次（点它 → 用库的口令 → 被拒 → 键盘没起来 → 只能再点它）。补空草稿是这个死循环唯一的出口，也是 reopen_entry 唯一新造草稿的场合。
  • 写盘判据跟着分开（Provenance）：构建时凭据与面板输入是设备学到的东西，关联成功那一刻写（照旧）；库交出来的那份是设备已经有的东西，不写。顺带修掉一处白写：开机自读那份原来每次开机都把同一条内容重写一遍（双槽轮写 = 一次擦写），现在不写；代价是点已存行连上不会把它顶到已存列表最前（remember 的置顶因此只发生在面板重新打了一次口令那种场合）。

射频这一半：Station trait 加了 begin_setup/end_setup 两条，bsp 把它们落成 Config::AccessPointStation(StationConfig::default(), ap)（APSTA，所以接入点开着的时候扫描照跑）与 Config::Station(...)。接入点是 AuthenticationMethodConfig::Open（按 esp-radio 1.0.0-beta.1 的 impl Default for AccessPointConfig 核过），名字来自板子自己的地址（vanling-<MAC 后两字节>，[测试] 三条钉住格式、去重与补零）而不是构建常量：同一个镜像刷两块板，在一个屋子里就是两个网络。

答复先到手机，再结束设置模式

provision::serve 返回 Infallible，所以在 configure 里它与面板那一路（setup_credential）select 竞争：谁先说出一个凭据谁结束设置模式，页面那一路随 select 一起被丢掉，接入点连同它的 Runner 一起下线。凭据经已有的 JOIN 平面走，于是 hold、凭据落盘、Provenance 全部原样复用 —— 页面与面板在「凭据从哪来」这层是同一条路。

页面在写答复并等到对端 ACK（TcpSocket::flush，语义按 embassy-net 0.9.1 的 tcp.rs 与它的文档）之后才把凭据投上 JOIN。这不是保守，是一条会稳定输的竞态：投上 JOIN 就意味 select 立刻解析、页面 future 与 AP 的 Runner 一起被丢掉，没有下一次 interface.poll —— 写进 socket 缓冲区、还没上介质的字节会随栈一起消失，手机看到的是一个永不回的请求。/submit 因此把完成页内联在 200 里而不是 302 到 /done：跳转要靠第二个请求，而第二个请求要等的那套栈已经不在了。

空闲退出，与仍然不做的 /exit

这一节上一版写的是「AP 一直在，直到有人交出一条凭据」：参考固件（../xiaozhi-esp32 的 78__esp-wifi-connect）的「定时重开 AP」与 /exit 都被判成恒等操作。两档前端落地之后前半条不再成立 —— AP 成了为手机专门拉起来的一档，没人看还开着，就等于给射程内任何人一台可以配网的设备；而「重开一遍」仍然没有意义，要收就收掉：

  • SETUP_IDLE_MS = 180_000：从 AP 这一档起来时计时，页面每答一次请求就重置（provision::page_read() 是只有最新值有意义的窗口，见 page_idle）。正在填表的手机不算空闲。
  • 时钟总是武装（page_idle()，不再有 armed）：有屏板到期回面板档；无屏板到期回已存网络（return None，link() 重新关联）；无屏且无存量网络的板子也一样收 AP —— 它回不去任何链路，这是 browsing() 的离线态。旧版那条「无屏且无存量 → 时钟不启动」的例外在第三版入口里删掉了：有屏板除复位+按住外，还能在离线页按 AP；无屏板只有复位+按住。一台出厂设备的开放 AP 不该一直广播（见「回到设置模式：启动页上按住 BOOT」）。
  • /exit 仍然不做：页面上没有它的位置，面板的 LEAVE/CLOSE/CANCEL 是同一件事更完整的说法，而 C6 的入口是启动页上那一下（见「回到设置模式：启动页上按住 BOOT」），不是页面里的一个链接。（页面的两个超时等的是「第一个字节」与「一条请求」，不是等空闲 —— 见台架一节 ④。）

设置模式下扫描不再等面板

[实测]：survey 在设置模式下无条件扫（扫描节奏本身没动，见「一轮扫描的节奏」），原来那道「等面板到达再扫」的阻塞门（PAGE.wait_for_list()）换成非阻塞的 PAGE.shows_list() 加一个上升沿。理由：C6 上没有人会到达那一页，而页面读的正是这条列表。面板到达时 SurveyHistory::clear() 仍在跑，所以「到达时看到的是现场」这条性质没变。

列表两份，因为有两个读者：面板那份走 SCAN 平面（渲染循环 take 掉），页面那份走 provision::LATEST。页面不能把面板那份取走；LATEST 是只有最新值有意义的窗口，所以是 Mutex<RefCell<...>> 而不是通道。

台架：从链接到手机，再到四轮修正（[实测]，2026-10-19）

C6 先跑通：手机连上 vanling-1234、拿到租约、页面自己打开（DNS 把任何名字都答成 192.168.4.1），再走 GET / → GET /scan（列出邻居）→ POST /submit（一条真口令）→ phase Connected；凭据落盘之后重刷同一个镜像仍然开机即连。S3 随后暴露了两个只有射频在环里才看得见的问题，另外两条是页面的答复本身太慢。

① 每轮扫描一次的 338 B 分配会打死 S3：第一次 /scan 之后 panic —— memory allocation of 338 bytes failed，堆上只剩 1,632 B。那一笔是列表的一份拷贝（Box<ApList>，四个邻居）。修的不是把它改小而是去掉：页面那份列表是「只有最新值有意义」的窗口，本来就该是静态量，于是回到 Mutex<RefCell<ApList>>，每轮扫描的分配归零 —— 代价从「运行时致命」换成「链接时算得清」。同一轮把每个页面 socket 的收发缓冲从 512 收到 256。

② 一个 socket 就是一条连接，而手机不止一条：Connection: close 意味着每一次 fetch 都是一条新连接，而手机后台同时还跑着连通性探测（generate_204）、mmtls 与预连接。一条 socket 的页面上 /scan 只能等前面几条腾出槽位 —— 40 s 窗口里只答了 2～3 条；加到两条仍是 2～3 条；三条才够。第三个 socket 的 StackResources 来自堆（Box::leak），.bss 一个字节没涨（SETUP_SOCKETS 仍是 5）。

③ 挂着的 socket 是「正在服务」，不是「可再挂」：armable(state) 只认 Closed 与 TimeWait；被 accept() 出来的 socket 在答复写完之前一直握在循环手里，这期间再 accept() 只会拿到 InvalidState。一度以为「写答复时也不停挂」能多答几条，实测相反：那会让页面自己的 /scan、favicon 与手机探测全被拒。

④ 两个超时，不是一个：连接建立起拿到第一个字节之间等 PENDING_TIMEOUT = 1 s（手机的预连接与被人放弃的连接就卡在这里），第一个字节之后换成 CONNECTION_TIMEOUT = 10 s。挑选顺序也改了：手上有数据的持有 socket 优先（can_recv()），其次任一持有 socket，最后才收新的 —— 一条真请求不该排在一条空闲连接后面。

读数（S3）：GET / 14 次、/scan 10 次、POST /submit 1 次（整轮 6,858 ms，其中页面那一次写 1,900～2,100 ms），日志形如 … answered Ok, 4468 B of body, in 2111 ms；读不动的连接印 a request would not be read after N ms: <err>（socket 超时与对端 RST 在日志里分不开，所以按耗时读）。页面自己的 /scan 重试阶梯是 5 次 × 320 ms，跨的正是 ② 里那几秒排队。

静态墙：同一把尺子（nm 取 _stack_start_cpu0 − _stack_end_cpu0）在这四条之后是 65,880 B，下限 65,536 B，余量 344 B；渲染循环自己的读数 [DISPLAY] stack peak 38592 B of 65880 B 与它一致。之后把设置模式这一支的注释与形状收了一遍（POST 那条路径同时改成不分配），[DISPLAY] main stack 现在读 65,912 B（余量 376 B），峰值仍是 38,592 B。[HEAP] … free with setup mode's future up 每次开机都印：S3 1,632 B、C6 41,056 B（那块 64 KiB 窗口用了约三分之一）。

刷新七八次就白屏：一次刷新要几条连接（[实测]/[测试]，2026-10-20）

台架报回来的是「刷七八次页面就白（转圈/报错）」——是页面下不来，不是手机掉线。上一轮把每个页面 socket 的收发缓冲从 256 B 抬到 1,460 B，修的是一页要几个往返（18 → 4），而这次的三笔账它一笔都没动：

账这一轮之前现在
一次刷新要几条连接页面 + /scan + 图标（含 .ico 的 204）+ 手机自己的连通性探测 = 3～6 条，对着 3 个页面 socket；多出来的握手被栈静默拒绝1 条（页面本身：图标内联成 data: URI、首屏列表内嵌进文档）；手机自己的探测仍是它自己的连接，答一次 302
页面在射频上做什么每 4 s 读一次 /scan，而设备对每一次 /scan 都 RESCAN.request() —— 页面开着就等于射频一直在扫只在按下「重新扫描」时走 GET /rescan；读列表（/scan）不再唤醒扫描
首屏等什么文档到了再 XHR 一次列表，列表才变成可点的行列表就在文档里，首屏即可点

为什么「页面自己在扫」是伤：设置模式的接入点是 APSTA，而逐信道扫描会打断客户端 —— 这正是 ESP-IDF 文档提醒、本记录对照表里标「未复现差别」的那一条。一次刷新 3～6 条连接、每条再叠一次立即重扫，七八次之后手机看到的就是一页没人答的网络。这一轮把两件都去掉，也就把那条 [据称] 从「扫描会打断客户端」改成「页面不该自己按扫描」。

内嵌列表是一个槽，不是模板：route::SEED_AT（/*scan*/）标记位置，页面在槽里放一份自己就能跑的 []（未替换时是一个空列表，不是语法错误），发送时 send_page 把 LATEST 的 JSON 写进槽、Content-Length 由 page_len(aps) = PAGE.len() − SEED_SLOT + scan_json_len(aps) 现算。这是这轮唯一会让「头说多少」与「写出去多少」分家的地方，所以两半都有测试：the_head_of_the_page_names_the_page_with_the_list_in_it（对着 json() 的实际长度）与 the_page_leaves_one_slot_for_the_list_and_it_stands_on_its_own。地址仍是等长替换（MAC_TOKEN），列表不是 —— 顺序也因此固定：地址在前、列表在后，两者各出现一次。

地址一律大写（AA:BB:CC:DD:EE:FF）。三个格式化器原本两套写法：面板表头与地址行是 mac_text（大写），手机页每行的 BSSID（scan 的 hex_digit）与面板上画不出的 SSID 退回成地址那一行（text::write_bssid）是小写 —— 同一个人手里两块屏对着同一个值看到两种拼法，面板上还可能在同一条行内撞上。统一到面板本来就在用的大写；ap_name（vanling-a1b2）不动，那是接入点的名字而不是地址显示，改大小写等于给设备改名。两个格式化器各补一条带字母的八位组的测试（原来的夹具全是全零/全数字地址，大小写根本分不出来）。顺带：名字画不出时名字行就是那个地址，那一行不再画第二行 —— 同一个字符串隔一行印两遍是多印的那一遍。

答完就 abort()：RST 把手机还没读走的字节丢掉（[实测]，2026-10-20 夜）

台架报回来的是偶发 ERR_CONNECTION_RESET：页面有时不出来，重刷又好。设备侧那几次日志全是 Get / answered Ok, 15,425 B of body, in 88–196 ms —— 字节确实写完了，坏在连接怎么结束：

  • close() + flush() 只等到自己的 FIN 被 ACK（FinWait2）。对端还没发 FIN，说明它可能仍在读。
  • 紧接着的 abort() 把 socket 置 Closed；栈看到 remote_endpoint 还在就发 RST（flush() 的 rst_pending 判据）。
  • RST 让对端内核丢弃接收队列里还没被应用读走的字节 —— 浏览器于是报 ERR_CONNECTION_RESET。

旁证三条：0 B 的答复（generate_204、/mmtls 的 302）从没失败过（一段就完，没有「还没读走」的窗口）；大页面每次都要多段；两块板共用这段代码，所以两块一起犯。

第一次修法是错的，而且错得有用：改成「等对端 FIN 再释放，上限 500 ms」之后，台架立刻报 ERR_CONNECTION_REFUSED。等 FIN 的 socket 不在监听：3 个页面 socket 里躺着一个在等，而手机一次刷新开 6 条连接，页面那条排到第 4 位时栈上没有监听者，SYN 直接被 RST。那几分钟日志正是这个形状：Get / 只有 3 条，其余全是 generate_204 重试。

实测把这笔等待算清了：flush() 返回时对端 FIN 已经在（TimeWait after 0 ms，455 次连接里 451 次），所以等它一分钱不花；上限收到 100 ms，只有 4/455 撞到（仍 FinWait2，那次 RST 落在对端早已不再读的时刻）。验收：55 次页面请求、0 失败（could not accept 0、did not finish 0）。

同一版把 send 的 Ok(0) 从静默返回改成记 an answer stopped N B short：抓到 3 次对端中途 reset（正文写到 9,171/15,710 B），以前这些是无声的。CONNECTION_TIMEOUT 也从 10 s 收到 3 s：只到了半截的请求不该占住 3 个页面 socket 之一十秒（一页本身约 100 ms）。

一条被推翻的假设：先在扫描上动过手 —— 页面每答一次就抬 PAGE_READ，扫描的暂停见到它就重新开始，理由是逐信道扫描把射频带离接入点信道（一轮 ≈1.15 s、暂停 5 s → 前几轮约 19% 时间不在信道上）。它确实生效：9 次刷新期间零条 survey found，前后两轮从 31 s 拉到 47 s。但页面照样失败，所以扫描不是病因。这段保留（有人在读页面时不该扫），别把它当成这次的修法。

尺寸：产品镜像 S3 1,025,680 / 6,291,456 B（16.30%），IOT_BOOT_PAGE=network 的 S3 镜像 1,027,424 B（16.33%）。静态墙这一轮小了：产品构建 65,720 B（余量 184 B），network 构建 65,688 B（余量 152 B）—— 上一轮同一块板印的是 65,816 B，少掉的 96/128 B 没有量到出处（不是等 FIN 的循环：它在设置模式的 future 里，属于堆）。余量只有三位数，记在这里。

无屏板的灯语（[测试]/[实测]，2026-10-23/24）

C6 只有一颗 WS2812，没有屏幕，所以配网状态只能由这颗灯说。灯语定在 core 的状态层（DeviceState::status_light），只在「有射频、无屏幕」的板上生效；S3 的屏幕照旧画它自己的页面与框。

设备状态灯为什么
从未配网（启动页结束之后）琥珀闪 3 下（160 ms 亮 / 160 ms 灭，约 0.8 s），随后页面灯出厂/离线待配网；这是公告，不是模式，亮完就把灯还给页面
AP 已开，等待手机蓝色慢呼吸（2 s，8→48）正处于配网模式；慢呼吸表示等待不是错误
未存盘的凭据正在关联/等地址蓝色快呼吸（0.8 s，16→64）手机刚提交的那一份；已存凭据的自动重连不走这条
关联成功（进入 Connected）绿色闪 3 下（100 ms 亮 / 100 ms 灭，约 0.5 s）成功是事件，不是模式；闪完页面灯接管
失败：找不到 AP（NotFound）琥珀闪 3 下人挪一下设备就能解决，不是口令错
失败：口令被拒等（其余 Failed）红色闪 3 下（120 ms 亮 / 120 ms 灭，约 0.6 s）AP 已经拆掉，手机看不到设备；红色表示「被拒绝」
已配网且在线不覆盖，显示页面自己的灯正常待机
已配网但暂时掉线不覆盖；一次断网只公告一次「有网络、只是不在线」是事件不是模式；重试不再反复闪，页面灯一直是底

优先级是一次性通知 > AP 配网模式 > 未存盘凭据的连接尝试 > 页面灯。成功/失败只在相位跳变的那一拍触发；一次断网由 outage_announced 锁住，幂等地只公告一次，Connected 时解锁，所以重试不会每 5 s 又把灯盖住。已存凭据的自动重连（saved == true）从不显示蓝色「连接中」，从开机第一秒起就是产品灯。通知的时钟属于渲染循环（tick_notice），状态层只保存当前该画哪一帧，因此宿主机测试能用普通数字驱动它。最后一闪在亮的边沿结束，不再留一段黑场。

接入点的 180 s 空闲时钟到点后，无屏且无存量网络的板子会收掉 AP、回到离线 browsing；这一路径在收 AP 后补发一条 setup = false 的链路报告，灯从蓝色回到页面灯，不再对已经关掉的模式继续说「配网中」。

几条规则是这一轮定下来的：

  • 两档不拆代码：configure 的两档共用 setup_credential、SurveyHistory、列表、页面、JOIN/FORGET/CANCEL；Front 只决定现在开着哪一档。两档是一个前端位 + 一个 AP 开关，不是两条路径 —— 拆成两条会让「切回来」变成第二次实现。
  • 口令由站点生成并持有：begin_setup(ssid, secured) 一次说清「开哪一种」，status() 读回 setup_password。面板从链路状态里拿到它、画进框里；页面不经过它，日志也不记值（只记位数）。
  • SetupPass 是定长窄类型（[u8; 10]），不是 Ssid：链路状态每个窗口都要拷一份，32 字节的名字字段装 10 字节的值，就是主任务每帧白付的 22 字节。这一条同时是过墙的手段之一（见下面的表）。
  • 字母表去掉 0/o/1/l：23456789abcdefghjkmnpqrstuvwxyz，31 个符号 × 10 位 ≈ 49.5 bit。把它从 320 px 的一行抄到手机键盘上，形近字符是唯一会出错的地方。
  • 默认口令按入口、不记住：启动页进档开放；运行中从 AP、LEAVE 或被拒后进档，有屏板默认 WPA2 + 随机 10 位，框里 PASS …，NO PASS 可把这一轮改回开放。切走再回来恢复入口默认；C6 无屏只能开放。代价见表。
  • CLOSE 与 CANCEL 不是一回事：框上右格 CLOSE 只把 AP 拆掉（回到面板档）；工具条左格 CANCEL 是退出设置模式、回去连已存的那条网络。后者只在有回头路（setup_cancellable）时画；没有已存网络时面板档的左格换成 SCAN、接入点档则整条只有 PANEL —— 一台空白设备从面板档进接入点档，再从接入点档回面板档，全程不碰「退出」。
  • 框里乱点不关 AP：answer_at 对两个按钮之外返回 None，让工具条继续命中；这一档里没有「任意一点关掉」，因为手指在框上乱点不该把手机正在填的 AP 拆掉。
  • 接入点档不按定时器扫描：survey_pause_after(Front::AccessPoint, …) 返回 None（不是零秒，是没有时钟）。进档时扫一轮填页面，之后只有页面自己的 RESCAN 要一轮。
  • 3 分钟（SETUP_IDLE_MS）：页面每读一次就重置，CLOSE 立刻拆。它约束的是接入点档比面板档多出来的那点代价：一个任何人都能连的网络在开着。代价是首屏不再广播 AP —— 一台刚开箱的设备在手机列表里是看不见的，得先有人按一下面板上的 AP；无屏板没有面板可按，入口是复位后在启动页按住 BOOT（见第三版入口一节），所以开箱设备同样不在手机列表里。

几何与文案：

  • 工具条两格在 core（ToolbarCell / toolbar_cell / toolbar_cell_at）：PANEL_COLUMNS/2 - TOOLBAR_GAP = 152 px 一格，8 px 的缝从格子里扣而不是加在格子外；PANEL_COLUMNS 整除两格、单格 ≥ TOUCH_MIN 都是编译期断言。缝不属于任何一格，但按中间的列切：x < PANEL_COLUMNS/2 是左格，其余是右格，8 px 里没有死区。
  • 左格：有回头路时 CANCEL，面板档没有回头路时 SCAN（一轮在飞时 WAIT），接入点档没有回头路时不存在；右格永远是 AP/PANEL —— 切档写目的地；有链路那一格是例外，LEAVE 写的是对链路做了什么（见「有链路那格改回 LEAVE」）。
  • 框：标题 SETUP MODE，两行正文 AP vanling-xxxx + PASS …（或 OPEN, NO PASSWORD），两答 NO PASS/PASS 与 CLOSE。两行正文的底边要压在框内答案之上，这是编译期断言（DIALOG_BODY_TOP + ROW_PITCH + FONT_H <= answer.y），PASS + 10 位 ≤ DIALOG_GLYPHS 也是。

真机上的三处：切档格、扫描格、框自己关掉（[实测]/[测试]，2026-10-20 夜第二版）

产品镜像烧上去，面板上三件事没成立：看不到切档那一格、看不到 SCAN、点了 AP 之后框起来又自己关掉。三处各有确定的代码路径，不是手感问题：

  • 左格不画、右格铺满整条。stamp_strip 原来在 !setup_cancellable 时只画右格，而右格那时用 toolbar_box() 铺满整条、只写 AP —— 于是 SCAN 整条消失，切档格看起来也不像一格。这台板子的 creds 是空的（没有任何已存网络），setup_cancellable == false 正是常态，不是边角。
  • 框自己关掉（这一条当时只找到了其中一半，另一半见下一节）。SetupAsk 是一个 embassy_sync::Signal：起 AP 要 ~1 s，这期间再点一下 AP（或第一下被读成两下），那个 Front 请求就留在平面上；下一个读它的是接入点档的循环，它立刻把 Front 读成「回面板」，框开了就关。请求是对哪一档发的，平面本身不记得。
  • 修法一：两格永远两格（工具条 A 案）。左格 = 有回头路时 CANCEL；面板档没有回头路时 SCAN（一轮在飞时 WAIT，与设置模式外同一个词）；接入点档没有回头路时不画左格、右格铺满整条 —— 接入点档没有列表可扫，画一个空半格就是个点不动的控件。右格永远是 AP/PANEL。state::toolbar 读同一组条件：左格 = 取消 / 重扫 / 切档。
  • 修法二：请求带上它是在哪一档发的（SetupAsk::{Cancel, Front, Pass} { from: Front }）。渲染循环发布时读当前 link.front，两档的循环各自只接 applies_to(自己的档) 的请求，其余的丢掉并记一行：dropped a setup request made on the panel's front; the access point stays up（另一个方向是 ... made on the access point's front; the box is not open）。没有时间窗：一条请求要么是这一档发的，要么不是。

setup_credential 进档先扫一轮，survey() 扫完发布的是 LinkStatus { setup: true, ..station.status() }。站点那份状态只知道射频那一半（相位、AP、地址、口令），不知道自己在哪一档：front 是默认的 Panel，setup_cancellable 是 false。于是每轮扫描都把这两格覆盖回去 —— 框被 shows_setup_box() 判成「不在接入点档」而消失；有已存网络的板子上 CANCEL 也会每 5 秒变成 SCAN 一次。这也解释了为什么它是自己关的：手指一次也没碰。

修法：LinkStatus::on_setup_face(front, cancellable)（core）把档位与回头路一次写好，相位/AP/地址/口令原样透传；网络任务四处发布（面板档、接入点档、扫描成功、扫描失败）都走它，survey() 拿的也是同一个 Face。

名字：PHONE → AP（同一轮）

PHONE 是按「你手里拿着什么」命名的：对笔记本不成立，也不是行业词。Espressif 把这整类叫 provisioning（SoftAP 与 WEB 两种传输），WLED、Tasmota、Shelly 一律叫 AP mode，而框里第一行本来就是 AP vanling-xxxx。于是：工具条右格 AP、内部 Front::AccessPoint、PHONE_LABEL → AP_LABEL；phone_idle → page_idle（它等的是页面请求，不是手机）。「用手机配网」这类叙述照旧 —— 说的是方法，不是档位名。

仍然只能靠眼睛/手指的：上面证明的是「档位不再被扫描改回去」，不是「框被画出来了」。所以还欠人一次：点 AP 后框应当一直开着、两格宽度与 AP 的字宽、框里两答；接入点档整条只有 CANCEL，面板档是 SCAN | AP。

有链路那格改回 LEAVE；网页那行改叫 AP MAC（[实测]/[测试]，2026-10-21）

真机上不对的是两句话，不是两处逻辑：

  • SETUP 看不出会断网：有链路时那一格上一轮按「动词写目的地」写成 SETUP，可是面板档没有 AP —— 进设置模式就等于离开这条链路，一个只写目的地的词把代价藏起来了。改回 LEAVE：框问 LEAVE "cafe"?，正文仍是 THE LINK GOES DOWN，两答 KEEP | LEAVE。落点没变（Hold::Left → unconfigured() 的面板档），出来时左格 CANCEL 把已存网络连回来 —— LEAVE/CANCEL 成对。切档仍写目的地（AP/PANEL）：不切过去就看不到那边，而离开这件事的意义就是代价本身，所以它是一条例外。
  • 网页那行的 BSSID 改叫 AP MAC：页头已经是 Device <本机 MAC>，行里那串是热点的 MAC。AP MAC 说清是谁的，不用术语也不和页头混。线上字段名仍是 "bssid" —— 那是协议，不是标签。
  • 离开链路回面板那一档，不是回手机上：front 原来在 link() 里是 let mut front = front;，和任务同寿，只有面板的 AP/PANEL 会改它 —— 链路起来、链路走后都不复位。于是用手机配过网的设备 front 停在 AP 档，之后在面板上按 LEAVE，unconfigured() 直接把 AP 又拉起来：面板上点的动作，下一个模式开在手机上。Setup 的注释只承诺「跨过被拒的凭据」（手机重输口令还留在手机页），从没说过要跨过成功入网。修法是 front_after_link(start, current, ended)：Left、Named 都回 build 的起始档（有屏 = 面板；无屏 = AP），Refused 留当前档。两条启动日志也补上了档位（on the {:?} front），否则下一次这种问题串口答不出来。
  • AP MAC 和地址挤成一条：标签与值原本是一个 textContent（'AP MAC ' + bssid），一个普通空格在 .72rem 的灰字里只有 3 px，读起来就是 AP MACA4:CF:…。拆成 .tag + .addr 两个 span，间距交给 gap: .5rem，地址提到 --ink；页头 Device <MAC> 的 <b> 一并提亮，两行同一套「灰标签 + 亮值」。

[测试] a_leave_names_the_network_the_link_is_on：format_question(Leave, link) = LEAVE "cafe"?；链路还没被接受（Connecting，没有 ap）时只写 LEAVE；Confirm::Leave.network(link) 就是链路的 AP —— 框后面被反白的行和问句点的是同一个名字。format_verb / format_body 的词与正文不变（LEAVE / THE LINK GOES DOWN）。工具条那格现在直接画 format_verb(Confirm::Leave)，和框里的答案同一个来源 —— 邀请和按钮不能再各说各的（the_boxes_words_are_the_verbs_own_and_fit_the_box 盯着这两处）。

[实测] 门禁：core 658 / app 35 / bsp 113；iot:lint、iot:check-host、iot:check-s3、iot:check-c6、iot:image 全过；nm 仍 65,592 B（余 56 B）—— 只是把 LinkStatus 多传进两个同步函数，没有跨 await 的新状态。

刷新不再 ERR_CONNECTION_REFUSED：keep-alive、六个监听位与半秒（[实测]/[测试]，2026-10-21）

C6 台架上手机打开设置页，浏览器报 ERR_CONNECTION_REFUSED。复位抓串口（[实测]，手机自己回来）：

[WIFI] Get /generate_204_<uuid> answered Redirect, 0 B of body, in 0 ms
[WIFI] a request would not be read after 0 ms: ConnectionReset
[WIFI] a request would not be read after 0 ms: ConnectionReset

探测那一条答了 302，接着两条连接被手机 reset，整段里没有一条 Get / —— 要的页面根本没到。「一次刷新只有一条连接」只算了文档自己，没算手机在文档旁边开的那些：预连接与系统探测几乎同时发 SYN，而 SETUP_SOCKETS = 5 是 DHCP 1 + DNS 1 + 页面 3。第 4 条 SYN 找不到监听者时栈直接回 RST，应用层看不到；Chrome 把这个 host 记成拒绝连接，连已经挂上的两条也一起丢掉（那两条 ConnectionReset 就是它丢的）。

三处修改：

  1. keep-alive（[测试]）：答复从 HTTP/1.0 … Connection: close 改成 HTTP/1.1 … Connection: keep-alive，Response::write_head(out, close) 里 close 是调用方唯一的话；answer() 在同一条连接上继续读下一个请求，空闲窗口 KEEP_ALIVE = 2 s。手机发 Connection: close（Request::close，逗号列表里带 close 也算）或请求本身命名网络（Action::Join，答完就要拆 AP）时才关。刷新因此复用已有连接，不再消耗监听位。pipelining 不支持：同一段里多出来的第二个请求随连接缓冲一起丢掉，浏览器不发。
  2. 页面监听位 3 → 6（PAGE_SOCKETS = 6，SETUP_SOCKETS = 2 + PAGE_SOCKETS = 8）：6 是 Chrome 每 host 的连接上限，盖住「探测 + 预连接 + 页面」这一次突发。
  3. PENDING_TIMEOUT 1 s → 500 ms：一句话都没说的预连接更快把监听位还回来。

堆的账（[实测]，C6 开机）：[HEAP] 32048 → 22168 B free with setup mode's future up，少 9,880 B —— 3 对 1,460 B 收发缓冲是 8,760 B，余下是 StackResources 多出的 3 个槽。页面 future 仍装箱在堆上，静态墙没动：nm 取 _stack_start_cpu0 − _stack_end_cpu0 = 65,592 B（下限 65,536 B，余 56 B）。S3 同一读数没有重取（那块板现在存着网络、不进设置模式），按同一差额估 25,560 − 9,880 ≈ 15,680 B。

尺寸：iot:image 的 S3 1,049,120 / 6,291,456 B（16.68%）、C6 813,424 / 1,048,576 B（77.57%）。

[未完成] 手机侧：C6 已烧这版镜像（开机 [HEAP] 22168 B），要人打开页面并连点十次刷新 —— 预期是十条 Get / answered Ok、零条 ConnectionReset、零条 would not be read；S3 的设置模式堆读数也要在那次一并确认。

done 页正常出现，设备随后加入网络。这 68 ms 究竟坏在「浏览器没画完」还是「Android 把配网门户那次导航作废」，手机侧分不开；两次运行之间只改了这 2 秒，所以按「答完就拆太快」记。同一段串口里页面的 Get / 有 4 次答完、另有几次 an answer stopped … B short: ConnectionReset —— 那是刷新时 Chrome 把上一条还没写完的加载取消掉，新的加载照常答（GET 会重试，POST 不会，这也是为什么只有提交会露出来）。

iot-core::drivers::network 里三条规则是产品决定而不是管道，所以放在能被测试打到的层：

  • 扫描结果按 BSSID 去重、按 rssi 排序、截断到 8 条。同名不同 AP 是两个网络（手机也这么显示），所以身份是 BSSID 而不是名字。
  • SSID 是字节。802.11 允许任意八位组，面板字库只有可打印 ASCII，所以「这个名字能不能画出来」是一个带退路的判断（画不出就显示 BSSID）。非 ASCII 的名字仍然逐字节保存（连接需要它），只是不可绘制。
  • 一轮扫描的节奏（5 s 一轮、空轮 1 s 后重试到连续三次为止、无人动过就退到 15/30 s）也是同一类政策，见「一轮扫描的节奏」。

Credentials::from_text 拒绝超长口令而不截断 —— 驱动也是拒绝，而截断过的口令对着任何东西都认证不上，读起来却像「密码错了」。

凭据走构建时环境变量（IOT_WIFI_SSID / IOT_WIFI_PSK，option_env!），不是 secret store：bench 镜像要说自己连的是哪个网络，而编进去的值就是构建命令行里的值。产品的凭据在面板输入、存 creds 分区（见「凭据落在哪」），绝不编译进固件。构建输入优先于已存列表：一个被指名了网络的构建只有那一条路可试（要改就改构建），而已存列表是「这设备被设置过」的答案。

回到设置模式：启动页上按住 BOOT（[测试]/[实测]，2026-10-21 第三版）

入口没变：两块板开机都先画 1.5 s 的启动页，按住 Boot 才进设置模式。理由照旧 —— 同一根手指在一台工作的设备上已经是页面自己的动词（Ambient 换模式、Speaker 静音），而 C6 要的是一次故意的仪式（先复位，再在窗口里按住），不是一条每三分钟能被一次长按打断的旁路。

这一版换掉的是这一按落到哪、以及启动页期间射频做什么：

事上一版这一版
启动页上长按Toolbar(Right)：有链路就离开，没有就 InvalidBusinessIntent::RequestSetup：只记请求（setup_wanted），不改页、不开 AP
启动页关闭回 boot_page请求过且 network_enabled → 落 Network；否则回 boot_page
启动页期间的链路读凭据、关联，长按再把它拆掉一条链路都不建：link() 先等 PAGE.wait_for_splash_end() 才读凭据
请求过之后先关联、再离开跳过关联：Front::AccessPoint 直接进设置模式
判断依据is_leavable() 看链路与链路无关：窗口内按下就算数，两块板同一个答案
无凭据开机自动进设置模式、AP 起来离线可用：不自动进设置模式、不起 AP
这一按的页面框直接叠在启动页上页先落 Network，link() 之后才拉 AP 档；启动页上不叠任何框

几条规则：

  • SPLASH_MS = 1_500。从 3 s 收到 1.5 s：长按阈值是 600 ms，1.5 s 仍容得下一次完整的按住；而手指刚离开复位键就能按到 Boot，再长只是让每次开机都慢一拍。窗口是「在 1.5 s 内开始按住」，不是「在 1.5 s 内按完」。
  • 判据是按下时刻在窗口内，不是松手在窗口内：时钟到期时若手指还按着（InputSource::held()，含去抖中尚未上报的释放），启动页等松手再关（app/src/input.rs）。1.4 s 按下、2.1 s 抬起那一下仍然算数，不会在按住的时候被时钟从手指下面抽走。
  • 一次性是结构上的：Splash 不在 CYCLE 里，next_page(Splash) 直接回 Ambient，with_boot_page 拒绝它，唯一的出口是输入任务到期报的 BusinessIntent::SplashOver（总线满时下一拍重试）。开机之后没有任何手势能回到这一页。
  • 落点是 boot_page，除非请求过：with_boot_page() 只记「启动页关掉之后落在哪」（构建输入 IOT_BOOT_PAGE、默认 Ambient；未 back 的页退回 Ambient）。SplashOver 读 setup_wanted：请求过且这块板开着网络，就落 Network；否则落 boot_page。启动页本身不改 state.page，所以 IOT_BOOT_PAGE=network 的 bench 构建照旧落在网络页。
  • 启动页期间一条链路都不建（[实测]）：link() 的第一件事是 PAGE.wait_for_splash_end()，它没结束时既不读凭据也不碰射频 —— 启动页窗口里不会出现 joining/leaving。请求过就直接 Front::AccessPoint 进设置模式，一次关联也不做；「先连上再拆掉」的写法会在这个窗口里留下两条日志，也会让 AP 档晚 2–3 s 才起来。
  • 无凭据 = 离线可用：first_saved() 为空时 browsing() 接住这台设备 —— 只在 PAGE.shows_list()（面板停在 Network 页）时扫描，页离开就停，JOIN 来了才 hold（此时才写盘）。不自动进设置模式，也不起 AP；面板页的两格仍在（SCAN | AP），点 AP 才把 AP 拉起来。C6 没有面板，配网仍要复位后在启动页按住 BOOT，这是它唯一的入口。
  • 面板页常驻：扫描、列表、键盘、JOIN 从设置模式的循环里拆了出来（setup_credential），link.setup 现在表示页面在设置面上：面板档不起 AP，接入点档才起。S3 无凭据时三击到 Network 就是活的列表（browsing()），左 SCAN 右 AP，点 AP 才拉 AP；点一行 → JOIN → hold。
  • 入口不止一个：离线页的 AP 格、有链路时面板的 LEAVE（Hold::Left）、已存凭据被拒（Hold::Refused）都进设置模式 —— 都是手指自己的动作。
  • 空闲时钟总是武装：page_idle() 不再看 armed；进 AP 档就起 180 s，页面每读一次重置，退出时有屏板回面板档、无屏板回已存网络。旧版「无屏且无存量 → 时钟不启动」的例外已经删掉：无屏板只有显式的复位+按住，有屏板另有离线页的 AP 格，一台出厂设备的开放 AP 不该一直广播。
  • 有屏板画三行（VANLING / HOLD BOOT / SETUP，bsp-esp 的 stamp_splash），行距 3 × FONT_H、按 width/height 居中。无屏板（C6）没有这页可看，状态照走：Boot 键那一按一样记下请求。

fast_connect（这一轮的新能力，[测试]）：

  • 每个存盘网络多带一个 LinkHint { bssid: [u8; 6], channel: u8 }（NONE = 未知）。关联时 Station::begin_connect_hinted 把它交给驱动：EspStation 覆盖成 config_for(credentials, hint)，ScanMethod::Fast + with_bssid/with_channel，驱动只去那个信道找那个 BSSID，不再全信道扫一遍。
  • 失败回退并重学：hint 那一轮失败（驱动拒收或关联超时）就 hint.take() 并 continue，下一次全扫；成功关联后用 status().ap 把新的 BSSID/信道写回（learn）。learn 只在值变了才写盘 —— 同一条网络、同一个信道不产生磨损。
  • 与 ESP-IDF 对照：wifi_sta_config_t 也是 bssid_set + bssid + channel 三个事实加 scan_method = WIFI_FAST_SCAN；本仓把同样三个事实存在凭据旁边，但不是「记住就信」：AP 换了信道、或同名 mesh 节点换了 BSSID 时，失败回退让 hint 成为一次尝试而不是一条硬约束。这是参考实现没写的那半步。
