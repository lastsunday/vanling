Wi-Fi 实现记录

apps/iot 的 Wi-Fi 链路：从「扫到哪些网络」到「拿到一个地址」。AI 产出，未经人类审阅，见上级说明。

每条判断标注依据：[测试] 有对应单元测试，[实测] 有硬件测量并附复现方式，[据称] 未复现、仅留痕。

状态

两颗芯片的探针都在台架上跑完（扫描 + 关联 + DHCP）。产品页分两片：只读的那一片已落地（DisplayPage::Network：阶段 + 当前 AP + 地址 + 扫描列表），第二片也落了盘（4×4 键盘、回显键、逐行滑动的列表、列表迟滞与缓存、选中行反色、开放网络、失败分档、扫描门控与退避，以及工具条：有链路时一个 LEAVE 按钮、无链路时一个 SCAN 按钮，前者执行前问一次、后者不问 —— 见「产品页」），凭据已落盘（creds 分区 + 自控槽格式，开机自己读回来、关联成功即写，见「凭据落在哪」），已存网络在列表里画 *、长按那一行 = 忘记，点一下已存的那一行就用设备自己存的那份口令去连（见「点已存的一行就用库里的口令」）。后四轮报来的缺陷与两处结构修正还在这份记录里。面板这条路有一条不需要手指的验法：IOT_PANEL_BENCH 构建开机后按面板自己的坐标把口令打一遍，再按工具条与确认框的坐标走完断开、点回那一行、断开、忘记、点回那一行、取消与重扫（见「按面板路径打字」与后四轮的读数）；它证明的是状态机与几何，而触摸手感与纯黑/背光仍要人点一次面板才算验过（板上只有 FT6336 产面板坐标，软件合成不了触摸）。状态层另有一层可达状态穷举（35 个动作、8,800 个状态、四条不变量，见「离开后点回那一行、以及一次丢掉的列表修正」）。未完成的事在文末；其余都在下面。

[实测，2026-10-16 更新] 表里 S3 的 65,536 B 是那天的预算。从今天起两颗芯片都是 49,152 B（S3 的 dram_seg 那一半从 32 KiB 收到 16 KiB，原因见下面「驱动的堆」那一节）。拿着凭据把 S3 探针重跑一遍（同一段扫描 + 关联 + DHCP）：

  • 驱动初始化 + 6 轮扫描在 48 KiB 下通过，没有 OutOfMemory；
  • 关联用 2,228 ms，此后 42 ms 拿到地址 192.168.1.136（开机后 9,337 ms 链路起来）；
  • 连上之后驱动堆 15,820 B 空闲 / 49,152 B（32.2%），85 秒里 38 次读数一条不差 —— 表里那天 S3 的 32,204 B 是 64 KiB 预算下的读数；
  • 产品镜像走同一条路：[WIFI] this build joins the network named …、associated、phase Connected，无 panic。

两块板看到的是同一批 AP（<ssid> 最强 −45…−50 dBm，ap1、ap5、ap6、ap7、aa:00:00:00:00:01 等），所以两张表之间的差别是 part 的差别，不是环境的差别。

esp-radio 官方文档给的 station 堆需求是 47–57 KiB（默认 ControllerConfig，高端那一档对应 6 个动态 RX buffer，正是本仓的取值）：32 KiB 会让 esp_wifi_init 直接 OutOfMemory。实测两颗芯片的驱动各用掉 33,332 B（S3）/ 35,028 B（C6）—— C6 多用 1,696 B，所以同一份代码在两颗芯片上要有两种给法（总数现在都是 49,152 B），见「同一套代码，两颗芯片」。

内存：三个决定（S3 上的账）

这一节讲 S3 的三个决定；C6 的对应选择在下面那一节。

驱动的堆：两块内部 DRAM，一块 32 KiB reclaimed + 一块 16 KiB dram_seg

[实测] esp-radio 是闭源 blob，通过 malloc 分配，所以符号必须在最终镜像里，esp-alloc 提供它们，而这个模块是背后的内存。

  • reclaimed 区（0x3FCF0000 以上）是二段 bootloader 留给 flash cache 的 DRAM，esp-hal 的链接脚本把它留给堆。但它的大小 = 64 KiB − 数据缓存，默认 64 KiB 缓存时这段是空的（本仓既有 ELF 在 0x3FCF0000 以上没有任何符号）。scripts/iot-xtensa.sh 把缓存压到 32KB，换来 32 KiB。
  • dram_seg 里那一半（先是 32 KiB，2026-10-16 收到 16 KiB）只有在 app 自己的堆搬去 PSRAM 之后才付得起（见下条）：那一步把主栈从 63,788 B 抬到 125,788 B，而实测峰值 39,809 B。这次收到 16 KiB 是另一条账：blob 的 IRAM 代码要在 dram_seg 里留一份同样大的镜像（31,980 B），加上产品自己的静态量之后静态量越过 RWDATA、主栈位置只剩 53,272 B（短断言 12,264 B），链接直接失败 —— 见「同一套代码，两颗芯片」里的驱动堆那一节。

两块都标 MemoryCapability::Internal：驱动的 pbuf 池要走 MAC 的 DMA，那条路到不了 PSRAM。

ESP_HAL_CONFIG_DATA_CACHE_SIZE 不能进 .cargo/config.toml：esp-config 把「对本芯片不生效的选项」当未知选项直接失败，而这个选项只在 S2/S3 生效，会把 C6 的构建炸掉。所以它放在 iot-xtensa.sh 里，并且按 --target 判定（无条件 export 时 moon run iot:check-c6 直接死在 esp-config 上）。

代价：面板与相机 DMA 在没有一半数据缓存的情况下跑。面板整帧是 DMA 写、渲染路径自己的工作集在内部 DRAM，所以量过的那几条路径不读它 —— 但这是预期不是实测，[INPUT] 的 17–25 ms 最坏 tick 与 AEC 那些数字需要重测。

app 的堆：搬进 PSRAM，因为没有第三处（S3）

[实测] 产品要装下 Wi-Fi，64 KiB 的 Rust 堆必须离开 dram_seg，而剩下的两处是：动相机那 150 KiB arena（已经在售的页面，要人点头），或者用板上那 8 MB octal PSRAM。chip_init_at 顺带把 PSRAM 映射好（Psram::new(PSRAM::steal(), PsramConfig::default())；那个 peripheral 是 Peripherals 的一个字段，直接取走是 partial move、函数返回不了整个结构体，steal() 拿到的是同一个 handle），app 的 main 再把堆指过去。

映射完必须自己验：写一个步长为 7 的图案再读回，两端各 4 KiB。esp-hal 只保证它把窗口映射出来，不保证这个 build 的 SPI 时序对，而 PSRAM 时序错了不 panic，是「十分钟后随机崩」。所以三种结果分开报：没有窗口 / 有窗口但读不回 / 可用，产品在第二种报错复位。台架实测：Ready(len: 8388608)。

PsramConfig::default() 不填 core clock：S3 的 SPI0/SPI1 挂在 APB 上，而 [set_cpu_clock] 只动 CPU 不动 APB，所以 CPU 频率不是 SPI 的源时钟，钉一个 core clock 就是拿一个不是源的时钟去除。

wifi_force_pd：补上 esp-radio 没人调的 init()（S3）

[实测] esp-radio 1.0.0-beta.1 里有一个 pub(crate) fn init()，负责开 modem 时钟、给 WiFi 域上电、脉冲复位、取 RTC 唤醒锁 —— 全 crate 没有任何调用者。本板实测停在 ROM 的 APB_CTRL.wifi_clk_en = 0xfffce030 与 dig_pwc bit 17（wifi_force_pd）= 1。chip-esp::ungate_radio() 现在代做这几条写（上游 init_clocks 与 enable_wifi_power_domain 的 S3 臂），探针在 take_wifi() 之前调用，实测 0xfffce030 → 0xffffdfdf、0x20000 → 0。

它没有让扫描变稳（改前 0/0/1，改后 0/1/1/1/1/1 与 1/1/0/1/0/1），所以射频的电源/时钟状态不是扫描抖动的成因。保留是因为谁也不该让驱动跑在上电状态没人设的射频上，不是因为它解决了什么。

同一套代码，两颗芯片

[实测] 探针与产品用的是同一份源码，两颗芯片各自构建各自烧录。差异全部落在 iot-chip-esp 之下，调用方看到的是一个入口：

iot_chip_esp::init_heap(&HEAP, HEAP_BYTES);   // 堆从哪来：这一句不问
iot_chip_esp::ungate_radio();                // 射频上电：这一句不问
let station = board.take_wifi();             // 射频是哪个 part 的：这一句不问

具体地，take_wifi() 的实现在两块板的板模块里各写一份（板层按构造就知道自己是谁），而 esp-radio 的 blob 由板特征选：lckfb-szpi-esp32s3 带 esp-radio/esp32s3、esp32c6-devkitc-1 带 esp-radio/esp32c6。esp-alloc 的芯片特征同理，从 radio 这个组件 feature 里挪到了芯片 feature 上（esp-alloc?/<chip>），因为「哪个 part 在编译」只有芯片 feature 知道；scripts/iot-feature-check.sh 现在把这套组合在两颗芯片上各编译一遍。

通用堆：S3 拿 PSRAM，C6 拿一块静态量

[实测] C6 没有 PSRAM（esp-hal 的 psram 模块按 soc_has_psram 编译，C6 不在其中），所以「app 的堆放 PSRAM」这条只在 S3 上成立。C6 的做法是芯片层里一块 64 KiB 的 dram_seg 静态量 —— 与产品入口原先自己声明的那块是同一块内存、同一节，搬进芯片层只是因为谁提供内存是 part 的事实，不是入口点该知道的事。两个 arm 的差别只在内存从哪来，HeapSource 只出现在日志里。

[实测] 入口点现在只有一句 init_heap，它同时管三件以前散在调用方的事：窗口从哪来、bytes 是否超出这块 part 能给的、要不到窗口时复位并留下原因（"this module has no PSRAM to map" / "PSRAM mapped and did not read back"，后者附上映射的大小 —— 那个数只在 init_psram 里还看得到，所以日志留在那里）。

驱动的堆：S3 两块，C6 一块

[实测] 两颗芯片现在是同一个总数 49,152 B（48 KiB）、不同的分法：C6 只有 dram_seg 一块 48 KiB，S3 是 32 KiB reclaimed + 16 KiB dram_seg。上板日志一行就是这两块：[WIFI] driver heap: 16384 B in dram_seg + 32768 B above it (dcache-reclaimed), both internal。

[实测] S3 的 dram_seg 那一半从 32 KiB 收到 16 KiB（2026-10-16），理由是上面那条账：blob 的 IRAM 代码要在 dram_seg 里留一份同样大的镜像（31,980 B），加上产品自己的静态量之后静态量越过 RWDATA 的末尾，主栈位置只剩 53,272 B（短断言 12,264 B），链接失败 —— 把常量改回 32 KiB 可以一行复现。收的是 dram_seg 那一半，不是 reclaimed 那半 —— 后者落在 0x3fcf0000，在 dram_seg 之外，本来就不占主栈。

四条约束决定了「48 KiB 分两块还是一块」：

  • #[ram(unstable(dcache_reclaimed))] 在 C6 上编不出来 —— 那个 procmacro feature 只由 esp-hal/esp32s3 打开（esp-hal/Cargo.toml 里它是 esp32s3 = [...] 的一行；esp32s2 也没开）。所以 reclaimed 那块是 S3 独有的，不是「忘了在 C6 上加」。
  • reclaimed 那块不占主栈，但不是白来的：它是二级 bootloader 的 flash cache 让出来的 DRAM，esp-hal 的链接脚本把它留给堆，代价是把数据缓存砍半（scripts/iot-xtensa.sh）—— 换掉的是缓存命中率。
  • C6 上没有第三个地方。它有 400 KiB 内部 DRAM；64 KiB 给 app 堆、48 KiB 给驱动堆之后，主栈实测 247,400 B（断言下限之上 181,864 B），其余是驱动的静态量。
  • 余量现在两边一样紧：C6 的驱动实测用掉 35,028 B（48 KiB 里余 28.7%），S3 用掉 33,332 B（48 KiB 里余 32.2%；用量是 10-15 那次在 64 KiB 预算下量的，预算本身今天上板量到）。调大 DYNAMIC_RX_BUFFERS 是两块板一起付账 —— 文档区间 47–57 KiB 的高端正是 6 个动态 buffer。

要把那 32 KiB 拿回来，唯一的路是把 blob 的 IRAM 代码送去 flash，本仓做不到。 esp-hal 的脚本里这件事得插在 .rotext_dummy 的预留和 rwtext.x 的归属规则之间，而两者在同一个生成文件里（ld/esp32s3/esp32s3.x），不在仓库手上。试过的做法（脚本排在 linkall.x 之前去抢那几段）链接是过的、镜像也是坏的：预留段永远落在 .text 之前，被送去 flash 的代码只能落在 IROM 原点 0x42000020，flash 偏移 0x20，和 .rodata 的头一页撞上 —— 段表里 paddr 就是它的 vaddr，两个段会写到同一片 flash。正路是给 esp-hal 加一个能容纳这件事的钩子（上游），不是本仓自己拼脚本。

扫描：一次不是测量，两次也是

[实测] 同一个镜像连刷三次，第一次扫描分别返回 0 / 0 / 1 个 AP。连扫 6 轮，两次开机：

开机 A:  0, 1, 1, 2, 2, 1 个
开机 B:  1, 1, 1, 2, 0, 0 个

结论只能是「单次扫描不是测量」：条数在同一次开机里就来回跳。附近最强的 AP 稳定在 −50 dBm，所以不是信号余量的问题。曾经写成过「第一次扫描永远是空的」，被开机 B 直接推翻（它第一次就有，而第 5、6 轮是空的）。

一轮扫描的节奏

产品只在扫描列表真的在屏上时才问射频（DisplayPage::Network，见「页面何时扫」）；只要在扫，节奏放在 iot-core::drivers::network（SURVEY_PAUSE_MS = 5_000、SURVEY_EMPTY_PAUSE_MS = 1_000、SURVEY_EMPTY_RETRIES = 3、空闲退避的 SURVEY_IDLE_PAUSE_MS = 15_000 / SURVEY_IDLE_MAX_PAUSE_MS = 30_000 / SURVEY_IDLE_ROUNDS = 3，判据是 survey_pause_after(empty_rounds, idle_rounds)），因为它和 MAX_LISTED_APS 一样是「怎么问射频」的政策，而不是循环的实现细节 —— 而且只有设备能跑到的路，必须由测试钉住。

规则三条：找到东西就歇满 5 s；空轮 1 s 后重试，但连续三个空轮之后就不再加急（第四个起按 5 s 的间隔）；连续三轮没人碰过面板就把间隔退到 15 s，再连续三次退到 30 s（idle_rounds 只被点击/滑动/换页清零）。后者是因为一个没人看的列表每 5.8 s 重扫一次，代价全在射频与主栈上，而屏幕上什么都没变。

[测试] 三条钉住它（a_survey_that_found_something_rests_the_whole_pause、an_empty_place_stops_being_retried_every_second、a_room_nobody_acts_on_is_read_less_and_less_often）。前两条是补的，因为上板先抓到了错：判据写成 *empty_rounds <= SURVEY_EMPTY_RETRIES 时，非空轮（计数为 0）也落进快重试那一支，日志立刻是每 1.8 s 一轮而不是 5.8 s。改完重刷，间隔回到 5.8 s，空轮那次重试在 1.76 s 后。

列表为什么不跳

[实测] 产品镜像 281 行的读数里，同一张列表在相邻两轮之间换过行序：每轮的条数 0 行 17 次 / 1 行 53 次 / 2 行 39 次 / 3 行 31 次 / 4–6 行 4 次，信道 11 的读数 σ≈3.1 dB（−81..−51）、信道 1 是 2.4、信道 6 是 2.1。而 rank_aps 本来就按信号从强到弱排 —— 所以「经常跳」不是排序错了，是每一轮都拿一次性的读数重排。

政策因此收进 core（SurveyHistory，core/src/drivers/network.rs），和 <n>-<m>/8 一样是「怎么读射频」而不是循环的实现细节：

页面何时扫

PagePlane（app/src/render.rs 的 PAGE）是页面状态的唯一共享读数：渲染循环每 pass 把 manager.state().page 发布进去，网络任务用 PAGE.wait_for_list() 等「列表在屏上」，并 select3 在「扫描间隔到」/「页面回到列表」/「staged 凭据就绪」之间醒。

放共享状态而不是加一条消息：页面是状态（幂等、只有最新值有意义），走 channel 就要一个深度 1 的队列、写者侧的变化检测、以及被拒发送时的重试 —— 三个只为绕开「状态被当消息送」而存在的机制。这与 EffectiveDemand 同一形状。

为什么门控在任务这里而不是让扫描自己判断：扫描是个死循环，它没有「页面」这个输入；把它接进来的是唯一能同时看到页面与射频的那一层。切页回来时 wait_for_list() 返回「等过」，所以退避计数被清零，进页立刻重扫一次。

[实测] 「回到列表」必须是边沿，不能是电平 —— 这是同一处第二次被上板推翻。第一版把 wait_for_list() 放在扫描间隔那一支的第三个分支上，而列表当时本来就在屏上：电平检查在第一次 poll 就满足，于是 5 s 的歇息被整段跳过。修好前一次 120 s 的读数：152 轮、相邻两轮相差 790 ms（survey found 的时间戳），退避一次都没生效 —— 也就是射频一直在扫，而屏幕上什么都没变。

修法是在 PagePlane 上加 wait_for_return()：先读当前页，再等它变化成列表页，于是「离开又回来」与「一直没离开」不再是一回事。它是边沿，wait_for_list() 是电平，两个都在用：前者给歇息当断路器，后者给循环问「现在该不该扫」。[测试] 一条钉住这个区别（a_rest_on_the_list_is_not_cut_short_by_the_list_being_up：同一个 plane 上，电平在列表上是 Ready，边沿是 Pending；先离开再回来才是 Ready）。

「已连接」= 关联 且 拿到地址，而地址要有人回说

[据称，来自参考固件] xiaozhi-esp32 的 WifiStation 里 WIFI_EVENT_STA_CONNECTED 的处理函数是空的，连接位是在 IP_EVENT_STA_GOT_IP 里置的。本仓库照这个口径：关联成功而没有地址的链路，产品在上面做不了任何事。

[实测] 带凭据跑起来才暴露：联上、拿到地址、40 秒报告全写 phase Connecting —— Connected 这个分支全仓没有任何一处赋值。地址归 embassy-net 的 stack 所有，而 Station trait 上只有 status()，拿到地址的那一层没有回说的接口。照这个接口做产品页，连上之后面板会一直显示「连接中」。

规则因此放进 core，成为可测的值而不是注释：LinkStatus::with_address(Option<Ipv4>)（有地址即 Connected；地址没了退回 Connecting；Failed 不被地址复活，三个 host 测试钉住）+ Station::note_address。调用点是每个报告窗口一次，不只是第一次 —— 租约失效只有那个循环看得见。改完再跑：phase Connected 稳 40 秒。

分区表

[实测] espflash 默认给 esp32s3 写 factory 1 MB，而本仓固件加 Wi-Fi 之前已经 630 KB。apps/iot/partitions/lckfb-szpi-esp32s3.csv 给 factory 6 MB，并带一个 4 KiB 的 phy_init。

phy_init 原本故意没写：esp-radio 的 Xtensa 构建把驱动的标定恢复钩子实现成 todo!()（ld/esp32s3_provides.x 把 misc_nvs_restore 绑到它，blob 里是未定义引用），而驱动看得见标定分区就会走那条路。[实测] 这条路走不到 —— 分区在场时 esp_wifi_init 不 panic，扫描正常。分区保留，它就是驱动第一次开机写下标定数据的地方。C6 那张也带 phy_init，同一个用途。

凭据落在哪（creds 分区）

esp-storage 0.10 + 自控槽格式，不引 NVS：NVS 是另一套带自己 KV 语义的 blob，而这一处要存的是一个定长列表，格式自己拿得住、能一行行读。

分区：两张板的表都加 creds,data,undefined,,0x2000,，紧跟 factory 之后，既有三条分区的偏移一格未动。[实测] 离线复验（espflash partition-table --to-binary <csv> -o pt.bin 再 --to-csv pt.bin）：S3 creds 落在 0x610000、C6 落在 0x110000，factory 仍是 0x10000。两个 4 KiB 槽（8 KiB）是双槽轮写要的：一次保存只写「上次没写的那一槽」，读的时候取 sequence 大的那条 —— 写到一半掉电留下的是另一条的旧副本，不是半条记录。子类型必须写名字（undefined = DATA_UNDEFINED 0x06）：写十六进制会让 esp-idf-part 在 unwrap() 上 panic（已在不烧板的前提下验过，见待办 5 的 ②）。

格式：core/src/drivers/credentials.rs。记录 = 12 B 头（magic VLNC + 版本 + 条数 + 体长）+ 每条 1 + 32 + 1 + 64 + 2 B + 4 B CRC，RECORD_BYTES = 1016，两条 const _: () = assert!(...) 钉住它装得进一个扇区；9 条宿主机测试钉住槽规则、「保存到一半丢电」与坏 CRC 的判读。

主栈的账（这是接线撞上的第四个问题，[实测]）：Store 值 ~1000 B（SavedNetworks 981 + 序号 + 槽号），而 serve/link/named_by_build/setup 都是同一个任务里的 async fn，每个按值携带它的帧都是主栈自己那一段的静态量（__embassy_main::POOL）。按值直传时 POOL 从 42,144 B 涨到 53,176 B，静态量越过 RWDATA 末尾 3,928 B，ld 报 stack.x:13 cannot move location counter backwards，主栈只剩 53,624 B（断言下限 65,536 B）。改成在板层装箱一次（Option<Box<CredentialStore>>，1 KB 落在 PSRAM 堆上）之后 POOL 只涨 976 B：[DISPLAY] main stack 65,944 B（bench 镜像）/ 66,168 B（产品镜像），对比 A 阶段的 67,704 / 68,600 B —— 这一整套功能净吃 ~1.8 KB，余量 408 B。这个余量就是下一次加静态量会撞到的墙，而撞到的是编译期断言，不是运行时的栈溢出。**再往后（工具条 + 掩码那一轮）**又吃掉一点，[实测] 链接期余量变成产品镜像 65,880 B（+344）、bench 镜像 65,560 B（+24）—— bench 那 320 B 差在它自己那批 log 的 Arguments 表落进 .data（render_loop 的 PanelBench 因此装箱，future 少 28 B 才重新过链接）。

面板分层那一轮（page::Part/page::walk + stamp::fill_surface）再量：产品镜像 +408 B（构建时给了网络的那一份）、bench 镜像 +88 B（docker run … espressif/idf-rust:esp32s3_1.95.0.0 里 nm … | grep _stack_，余量 = _stack_start − _stack_end − 65536）；不给网络、只带 IOT_BOOT_PAGE=network 的产品镜像（就是这一轮最后烧在板上那份）是 +376 B，两份差的 32 B 在编译进去的那几个字符串上。这一轮没有新的 static：两个镜像的具名静态量逐字节同名同尺寸（各 308,284 B，nm --size-sort --print-size 对齐后无差），新增的全是 .text（产品 +15,404 B、bench 更多）。两者那 320 B 的差还是上面那句里的无符号段（.data 开头到第一个具名符号之间：产品 9,168 B、bench 9,480 B）—— 所以两个镜像的余量不能互相比较代码，只能同一个镜像前后比。

特征与分层落点

wifi 是元件 feature（模块轴），在 iot-bsp-esp 里一个文件一个模块，门控只在 components/mod.rs 一处；两块板的板 feature 都聚合它（两块板都有射频焊在板上）。iot-core 零 cfg：能力经组合点注入（HasWifi）。components/wifi.rs 本身跨芯片可用 —— 它只拿 peripherals::WIFI 与驱动的类型，两颗芯片各编译过一遍。

Station 的方法用 RPITIT 返回 impl Future，不要 + Send：产品把这些 future 与 input/render/control/feed 一起 join 在同一个任务栈上，没有 spawn。（Speaker 需要 Send 是因为它的 feed 在独立的高优先级 executor 上。）

take_wifi() 不能在 Board::new 里做：驱动的启动需要调度器已经跑起来（esp_rtos::start() 在 app 的入口里），所以板子交出的是外设而不是 station。

iot-chip-esp 的两个芯片 feature 各带五个芯片 feature 转发（esp-hal / esp-rtos / esp-println / esp-backtrace / esp-bootloader-esp-idf），console 另是一条轴（console-auto / console-uart），app 转发过来。原因是那三个 crate 的 build script 各自要求「恰好一个芯片 feature」和一个 console，平时都由 app 顺手给，于是任何没有 app 在场的构建死在别人的 build script 上 —— iot-feature-check.sh 第一次真跑到 wifi 就抓到了。这就是 features.md 规则 5：用到的每一处都要自己写出来。

手势删减：延迟在分类器里，不在面板

[测试] 触摸现在只剩 Press / Tap（抬指即发） / Swipe / LongPress / Ghost（GestureEvent::DoubleTap 与 TripleTap 已从词汇表删除，TouchDiagnostics 里那两个计数一起去掉）。

延迟的根因是点击曾经被含在嘴里：旧的 TouchGestures 把一次短抬存进 chamber（PendingTap），只有在 DOUBLE_CLICK_WINDOW_MS = 400 的窗口过期那一次 tick 里才发布 —— 也就是每一次点击都要等最多 400 ms 才被看见，页面跟着晚 400 ms 反应。删掉触摸多击之后 Tap 在抬指那一次采样上发布；多击窗口只留给硬件按钮（切页唯一的入口是硬件三连击，那是真按钮，窗口照旧 400 ms）。

GestureEvent::Tap 带 at_ms（抬指时刻），位置改报按下沿（down_x/down_y）而不是抬指坐标：面板粗糙，抬指坐标会漂；键盘用 at_ms 判断 800 ms 内的第二击是「换候选」而不是「又一个字符」。TouchGestures 的队列同时从 2 槽放宽到 4 槽（一次采样最多产出「两个触点各一个手势 + 这一次运行的幽灵脉冲」），满了丢最旧的。

点已存的一行就用库里的口令（[实测]，2026-10-17 第五轮）

已存网络（画 * 的那一行）点一下 = 用设备自己存在 creds 里的那份口令去连，不再让人重打一遍。这一条把凭据那条路上的所有权分开：口令库只有网络任务一个所有者（SavedNetworks 从不进 DeviceState —— S3 静态内存墙下那 980 B 落不成值，见「凭据落在哪」），页面能说的是「哪个网络」而说不出「它的口令是什么」；于是页面点一下只交名字，答复（库里有没有、能不能连）由射频给。

  • 请求是同一个平面的两种形状。CredentialPlane/CREDENTIALS 改名 JoinPlane/JOIN，消息由 Credentials 变成 JoinRequest::{Typed(Credentials), Held(Ssid)} —— 同一个请求「帮多少忙」的两种，还是同一条单槽平面（不新开平面、不新加一条 select 臂）。DeviceState.credential 因此变成 DeviceState.join: Option<JoinRequest>（take_join()）：字段还是那一个，宽度只多一个判据字（Credentials 已是两个变体里宽的那个），没有新的 static。
  • 库里没有就回报页面。网络任务在两个读这条平面的地方（setup 的开头、以及链路已起时 hold 的窗口）都走同一个 asked_for()：Typed 直接用（Provenance::Named）；Held(name) 走 SavedNetworks::copy_of(name) 查库 —— 查到就用那份（Provenance::Stored），查不到就发 BusinessIntent::NoCopy(name)（走既有 INTENT_BUS，与 Link 报告同一条路）。页面收到后 no_copy()：只对当前选中的那一行成立（这期间点了别的行就是更新的问题，旧答复丢掉），升键盘问口令。
  • 被拒之后不落到死循环上。库那份也会被拒（对面改了口令）。那时 refused 照旧，而 reopen_entry 补一条选中的行没有草稿就造一个空的：键盘是拿草稿画的、工具条又被键盘藏起来，所以「有键盘、没草稿」是一页什么都点不到的东西 —— 而这一行偏偏只会被点第二次（点它 → 用库的口令 → 被拒 → 键盘没起来 → 只能再点它）。补空草稿是这个死循环唯一的出口，也是 reopen_entry 唯一新造草稿的场合。
  • 写盘判据跟着分开（Provenance）：构建时凭据与面板输入是设备学到的东西，关联成功那一刻写（照旧）；库交出来的那份是设备已经有的东西，不写。顺带修掉一处白写：开机自读那份原来每次开机都把同一条内容重写一遍（双槽轮写 = 一次擦写），现在不写；代价是点已存行连上不会把它顶到已存列表最前（remember 的置顶因此只发生在面板重新打了一次口令那种场合）。

纯逻辑部分（宿主机可测）

iot-core::drivers::network 里三条规则是产品决定而不是管道，所以放在能被测试打到的层：

  • 扫描结果按 BSSID 去重、按 rssi 排序、截断到 8 条。同名不同 AP 是两个网络（手机也这么显示），所以身份是 BSSID 而不是名字。
  • SSID 是字节。802.11 允许任意八位组，面板字库只有可打印 ASCII，所以「这个名字能不能画出来」是一个带退路的判断（画不出就显示 BSSID）。非 ASCII 的名字仍然逐字节保存（连接需要它），只是不可绘制。
  • 一轮扫描的节奏（5 s 一轮、空轮 1 s 后重试到连续三次为止、无人动过就退到 15/30 s）也是同一类政策，见「一轮扫描的节奏」。

Credentials::from_text 拒绝超长口令而不截断 —— 驱动也是拒绝，而截断过的口令对着任何东西都认证不上，读起来却像「密码错了」。

凭据走构建时环境变量（IOT_WIFI_SSID / IOT_WIFI_PSK，option_env!），不是 secret store：bench 镜像要说自己连的是哪个网络，而编进去的值就是构建命令行里的值。产品的凭据在面板输入、存 creds 分区（见「凭据落在哪」），绝不编译进固件。构建输入优先于已存列表：一个被指名了网络的构建只有那一条路可试（要改就改构建），而已存列表是「这设备被设置过」的答案。
