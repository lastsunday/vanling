Wi-Fi Implementation Record

The Wi-Fi link in apps/iot, from "which networks are out there" to "the device has an address". AI output, not reviewed by a human — see the parent note.

Each judgement carries its basis: [test] a unit test pins it, [measured] a hardware measurement, [as-reported] not reproduced, left as a trace.

State

The probe has run end to end on both parts (scan, associate, DHCP). The product page lands in two slices: the read-only one is in (DisplayPage::Network: phase, the access point in use, the address, and the scan list), and the second slice is in as well (the 4 × 4 keyboard, the reveal key, a list that slides a row at a time, hysteresis and caching for the list, the selected row reversed, open networks, failure classes, the page-gated survey with its backoff, and the action strip — a LEAVE button when there is a link and a SCAN button when there is not, the first asking once before it acts and the second not asking at all — see "The product page"), the credential is kept on the part (a creds partition and our own slot format; read back at boot and written the moment an association succeeds — see "Where a credential lives"), a stored network carries a * in the list, with a long press on its row to forget it, and a tap on a saved row joins it with the copy of the passphrase the device keeps (see "Tapping a saved row joins it with the copy the device keeps"). The defects the four later rounds reported, and the two structural corrections, are still in this record.

That path has an answer that needs no finger: an IOT_PANEL_BENCH build types the passphrase at its own drawn coordinates at boot, then walks the action strip and the confirmation at their own drawn coordinates too — the strip, the row it was just taken off, the leave, the forget, the row again, cancel, look around (readings in "Typing along the panel's own path" and the later runs). What it proves is the state machine and the geometry, while the touch's feel and the black ground are still a human's to confirm (only the FT6336 produces panel coordinates on this board; touch cannot be synthesised in software). The state layer also gained a reachable-state sweep (35 moves, 8,800 states, four invariants — see "Tapping back into the row a link was left from, and one dropped list correction"). A board with no panel has a front door now too: iot-core::provision is the protocol (45 host tests), iot-app::provision wires it to an open access point + DHCP + an answer-everything name server + a config page, and configure races it against the panel's own path through select (see "How a board with no panel gets configured"); the panel's path itself is untouched. Both boards have since walked that door on the bench (the C6 end to end, the S3 after three fixes — see "The bench: from link, to phone, with four corrections").One way back into setup mode is the splash page: both boards draw it for 1.5 s at boot, holding BOOT during it asks for the mode and lands on the network page, and no link is built during those 1.5 s (see "Getting back to setup: hold BOOT on the splash page"). No credentials means an offline device: no setup mode of its own and no access point, the panel's page scans only while somebody is on it (it still offers SCAN | AP, and AP is what raises the access point — secured on a board with a panel), and a saved network carries its BSSID/channel so the next boot goes straight there (fast_connect). The config page is on its third version: the first list is embedded, the icon is inline, a reload costs one connection, and only the button wakes a scan — the language switch sits in the header, the passphrase is a bottom sheet and each row carries its BSSID (see "Seven or eight reloads and the page goes white"); the panel's list rows gained that network's own BSSID on the same day (a second line under the name, same section). The loose ends are at the bottom.

Memory: three decisions (the S3's budget)

This section is the S3's three decisions; the C6's counterparts are in the section below.

The driver's heap: 32 KiB reclaimed + 16 KiB dram_seg

[measured] esp-radio is a closed blob that allocates through malloc, so the symbols have to exist in the final image. esp-alloc provides them; this module is the memory behind them.

  • The reclaimed region (above 0x3FCF0000) is DRAM the second-stage bootloader used for its flash cache, which esp-hal's linker leaves to the heap. Its size is 64 KiB minus the data cache, so it is empty at the default 64 KiB cache (the existing ELF in this tree has no symbol above 0x3FCF0000). scripts/iot-xtensa.sh halves the cache to buy 32 KiB back.
  • The dram_seg half (32 KiB at first, cut to 16 KiB on 2026-10-16) is affordable only because the app's own heap moved to PSRAM (next): that took the main stack from 63,788 B to 125,788 B with 39,809 B in use. This cut is a different bill: the blob's IRAM code reserves a mirror of its size (31,980 B) in dram_seg, and once the product's own statics are added the statics run past the end of RWDATA, leaving the main stack's slot at 53,272 B — 12,264 B under the assertion — so the link fails — see the driver's-heap section under "One source, two parts".

Both are MemoryCapability::Internal: the driver's pbuf pools go to the MAC's DMA, and that path cannot reach PSRAM.

ESP_HAL_CONFIG_DATA_CACHE_SIZE cannot live in .cargo/config.toml: esp-config treats an option that is not active for the chip being built as an unknown one and fails outright, and this one is active on the S2 and S3 only, so an [env] entry breaks the C6 build. It lives in iot-xtensa.sh instead, keyed off --target (exported unconditionally it killed moon run iot:check-c6 inside esp-config).

The cost: the panel and camera DMA now run with half the data cache. Whole frames are written by DMA and the render path's working set is internal DRAM, so the measured paths do not read it — but that is an expectation, not a measurement, and [INPUT]'s 17–25 ms worst tick plus the AEC figures need re-measuring.

The app's heap: PSRAM, because there is no third place (S3)

[measured] For the product to carry Wi-Fi, its 64 KiB Rust heap has to leave dram_seg, and two places were left: the camera's 150 KiB arena (a page that already ships, needs a human's agreement) or the board's 8 MB octal PSRAM. chip_init_at maps the PSRAM on the way past (Psram::new(PSRAM::steal(), PsramConfig::default()) — that peripheral is one field of Peripherals, so taking it out is a partial move and the function could not hand the whole struct back; steal() yields the same handle), and the app's main points the heap at the window.

The mapping has to be proved afterwards: a pattern stepping by seven, written and read back over 4 KiB at each end. esp-hal only promises that it mapped a window, not that this build's SPI timing is right — and wrong PSRAM timing does not panic, it corrupts something ten minutes later. So the three outcomes are reported apart: no window / mapped but the pattern did not read back / ready, and the product resets on the second. Measured on the bench: Ready(len: 8388608).

PsramConfig::default() names no core clock: the S3's SPI0/SPI1 hang off APB and [set_cpu_clock] moves the CPU while leaving APB alone, so the CPU frequency is not what the SPI block is clocked from — pinning one would divide by a clock that is not the source.

wifi_force_pd: doing the init() esp-radio never calls (S3)

[measured] esp-radio 1.0.0-beta.1 carries a pub(crate) fn init() that un-gates the modem clocks, powers the WiFi domain up, pulses its reset and takes the RTC wake lock — and nothing in that crate calls it. This part sits at the ROM's APB_CTRL.wifi_clk_en = 0xfffce030 with bit 17 of dig_pwc (wifi_force_pd) set. chip-esp::ungate_radio() now makes those writes (the S3 arms of upstream's init_clocks and enable_wifi_power_domain), the probe calls it before take_wifi(), and the registers move: 0xfffce030 → 0xffffdfdf, 0x20000 → 0.

It does not steady the scan (0/0/1 before, 0/1/1/1/1/1 and 1/1/0/1/0/1 after), so the radio's power and clock state is not what makes the scan wobble. The writes stay because no driver should run on a radio whose power state nobody set — not because they fixed anything.

One source, two parts

[measured] The probe and the product are the same source, built per part and flashed to each. Every difference lives below iot-chip-esp, and a caller sees one entry point:

iot_chip_esp::init_heap(&HEAP, HEAP_BYTES);   // where the heap comes from: not asked
iot_chip_esp::ungate_radio();                // powering the radio: not asked
let station = board.take_wifi();             // which part's radio: not asked

take_wifi() has one implementation per board module — a board knows what it is by construction — and the driver's blob is the board feature's choice: lckfb-szpi-esp32s3 carries esp-radio/esp32s3, esp32c6-devkitc-1 carries esp-radio/esp32c6. esp-alloc's chip feature moved the same way, from the radio component feature onto the chip features (esp-alloc?/<chip>), because only a chip feature knows which part is being compiled; scripts/iot-feature-check.sh now builds that combination on each part.

The general heap: PSRAM on the S3, a static on the C6

[measured] The C6 has no PSRAM — esp-hal's psram module is behind soc_has_psram and the C6 is not in it — so "the app's heap goes to PSRAM" holds on the S3 alone. The C6 gets a 64 KiB dram_seg static in the chip layer instead, which is the same block of memory in the same section that the product's entry point used to declare for itself: it moved because where memory comes from is a fact about the part, not something an entry point should know. The two arms differ only in where the window is, and the source appears in the log and nowhere else.

[measured] An entry point now says init_heap once, and that one call does three things that used to sit with the caller: finding the window, checking that bytes fits what this part can offer, and — when there is no window — resetting with the reason ("this module has no PSRAM to map" / "PSRAM mapped and did not read back"). The second reason carries the mapped size, and init_psram is the only place that can still see it, so that log line lives there.

The driver's heap: two blocks on the S3, one on the C6

[measured] Both parts now total 49,152 B (48 KiB), split differently: the C6 has one dram_seg block of 48 KiB, the S3 has 32 KiB reclaimed plus 16 KiB of dram_seg. One line of the board log is those two blocks: [WIFI] driver heap: 16384 B in dram_seg + 32768 B above it (dcache-reclaimed), both internal.

[measured] The S3's dram_seg half went from 32 KiB to 16 KiB (2026-10-16) for the bill above: the blob's IRAM code reserves a mirror of its size in dram_seg (31,980 B), and with the product's own statics the statics run past the end of RWDATA, leaving the main stack's slot at 53,272 B — 12,264 B under the floor — so the link failed, and putting the constant back is a one-line repro. What was cut is the dram_seg half, not the reclaimed one: the latter lands at 0x3fcf0000, outside dram_seg, and never took main stack.

Four constraints decide whether 48 KiB is two blocks or one:

  • #[ram(unstable(dcache_reclaimed))] cannot compile on the C6. The procmacro feature is opened by esp-hal/esp32s3 alone (it is one line of the esp32s3 = [...] group in esp-hal's Cargo.toml; esp32s2 does not open it either), so the reclaimed block is the S3's alone rather than something that was forgotten on the C6.
  • The reclaimed block takes no main stack, but it is not free: it is DRAM the second-stage bootloader used for its flash cache, which esp-hal's linker leaves to the heap, and the price is halving the data cache (scripts/iot-xtensa.sh) — what is traded away is cache hits.
  • The C6 has no third place. It has 400 KiB of internal DRAM; with 64 KiB for the app's heap and 48 KiB for the driver's, the main stack measures 247,400 B — 181,864 B above the floor — and the rest is the driver's statics.
  • Both parts are equally tight now: the C6's driver measures 35,028 B used (28.7% headroom of 48 KiB) and the S3's 33,332 B (32.2% headroom of 48 KiB; the usage is the one measured on 10-15 under the 64 KiB budget, while the budget itself was measured on the board today). Raising DYNAMIC_RX_BUFFERS is a bill both parts pay — the high end of the documented 47–57 KiB range is exactly the 6 dynamic buffers this build sets. It is on the list at the bottom.

Getting that 32 KiB back means sending the blob's IRAM code to flash, and this repository cannot do it. In esp-hal's script the rule would have to sit between .rotext_dummy's reservation and rwtext.x's ownership rule, and those two live in the same generated file (ld/esp32s3/esp32s3.x), which is not ours to edit. The attempt that was tried (an earlier script claiming those sections before linkall.x) links but produces a broken image: the reservation always lands before .text, so code sent to flash can only land at the IROM origin, 0x42000020 — flash offset 0x20 — on top of .rodata's first page; in the ELF the segment's paddr is its vaddr, so two segments end up writing the same flash. The right route is a hook esp-hal can expose (upstream), not this repository assembling its own script.

Scanning: one round is not a measurement, and neither is two

[measured] One image, three boots, and the first scan returned 0 / 0 / 1 access points. Six rounds in a row, two boots:

boot A:  0, 1, 1, 2, 2, 1
boot B:  1, 1, 1, 2, 0, 0

The only conclusion that survives: one scan is not a measurement. The count moves between 0 and 2 within a single boot. The strongest AP nearby sits at a steady −50 dBm, so this is not a signal-margin problem. It was briefly written as "the first scan is always empty" and boot B contradicted it outright — one AP on the first round, nothing on rounds 5 and 6.

The dwell decides how complete the list is (1–2 → 1–6), at the cost of a user's wait going from 0.15 s to 0.8 s. The camera decides whether a whole round comes back empty, with no mechanism yet: it is a continuously running DVP DMA on the same core as the WiFi driver task, so bus or interrupt contention is the obvious suspect. That does not block delivery — a page that keeps scanning while the list is empty is fine, which is what the probe does (SCAN_ROUNDS = 6, 500 ms apart).

The rhythm of a round

The product asks the radio only while the scan list is really on the panel (DisplayPage::Network — see "When the page scans"). While it is scanning, the rhythm lives in iot-core::drivers::network (SURVEY_PAUSE_MS = 5_000, SURVEY_EMPTY_PAUSE_MS = 1_000, SURVEY_EMPTY_RETRIES = 3, and the idle backoff's SURVEY_IDLE_PAUSE_MS = 15_000 / SURVEY_IDLE_MAX_PAUSE_MS = 30_000 / SURVEY_IDLE_ROUNDS = 3, decided by survey_pause_after(empty_rounds, idle_rounds)) because, like MAX_LISTED_APS, it is a policy about how the radio is asked rather than an implementation detail of the loop — and a path only the device can run has to be pinned by a test.

Three rules: a round that found something rests the whole 5 s; an empty round is retried after 1 s, but three empties in a row are the end of that (the fourth takes the 5 s rest); and three rounds nobody acted on push the rest out to 15 s, then three more to 30 s (idle_rounds is cleared by any tap, any slide of the list, or the page appearing). The second exists because a place with nothing in range — a device in its factory state, an access point that is off — answers every round the same way, and asking every second is the radio scanning for most of every second. The third because a list nobody is looking at, rescanned every 5.8 s, spends the radio and most of the main stack drawing nothing new.

[test] Three tests pin it (a_survey_that_found_something_rests_the_whole_pause, an_empty_place_stops_being_retried_every_second, a_room_nobody_acts_on_is_read_less_and_less_often). When the page scans

PagePlane (PAGE in app/src/render.rs) is the only shared reading of the page: the render loop publishes manager.state().page once a pass, and the network task waits on PAGE.wait_for_list() for "the list is on the panel", waking on select3 between "the scan interval is up", "the page has come back to the list" and "a staged credential is ready".

Shared state rather than one more message: a page is state (idempotent, with only the latest value meaning anything), and a channel would need a one-deep queue, change detection on the writer side and a retry for a refused send — three mechanisms that exist only to work around a state being sent as a message. It has the same shape as EffectiveDemand.

The gate is in the task rather than in the scan itself because the scan is a loop with no "page" input; the layer that can see both the page and the radio is the one that connects them. Coming back to the page, wait_for_list() reports that it waited, so the backoff counters are cleared and the page is scanned again at once.

[measured] "Back on the list" has to be an edge, not a level — this is the second time the board overturned this one spot. The first version put wait_for_list() in the third arm of the scan-interval select, and the list was already up at that point: a level check satisfies its first poll, so the entire 5 s rest was skipped. The reading before the fix, over 120 s: 152 rounds, adjacent rounds 790 ms apart (the survey found timestamps) — the backoff never once took effect, which is to say the radio scanned continuously while nothing on the panel moved.

The fix is wait_for_return() on PagePlane: read the page now, then wait for it to change to the list's, so "left and came back" stops being the same thing as "never left". It is an edge; wait_for_list() is a level, and both are in use: the edge is the rest's circuit breaker, the level is how the loop asks "should I be scanning at all". [test] One test pins the difference (a_rest_on_the_list_is_not_cut_short_by_the_list_being_up: on one plane, the level is Ready while the list is up and the edge is Pending; only away-then-back is Ready).

"Connected" means associated and addressed, and somebody has to say so

[as-reported, from the reference firmware] In xiaozhi-esp32's WifiStation the handler for WIFI_EVENT_STA_CONNECTED is empty; the connected bit is set from IP_EVENT_STA_GOT_IP. This repository uses the same rule: a link with no address is one the product cannot do anything with.

[measured] Only the credentialed run exposed it: associated, addressed, and forty seconds of reports all saying phase Connecting — nothing in the tree ever assigned Connected. The address belongs to embassy-net's stack and the Station trait had only status(), so whoever holds the address had no way to say so. A product page built on this interface would say "connecting" forever while passing traffic.

The rule therefore lives in core as a testable value rather than a comment: LinkStatus::with_address(Option<Ipv4>) (an address makes it Connected, losing the address goes back to Connecting, a Failed is not resurrected — three host tests pin it) plus Station::note_address. The call site is once per report window, not only the first: only that loop can see a lease lapse. After the change: phase Connected, steady for forty seconds.

The partition table

[measured] espflash writes a 1 MB factory partition for the esp32s3 by default and this firmware was already 630 KB before the Wi-Fi blobs. apps/iot/partitions/lckfb-szpi-esp32s3.csv gives factory 6 MB and carries a 4 KiB phy_init.

phy_init was deliberately left out at first: esp-radio's Xtensa build implements the driver's calibration-restore hook as todo!() (ld/esp32s3_provides.x binds misc_nvs_restore to it, and the blob references it undefined), and the driver reaches for that path once it can see a calibration partition. [measured] it does not reach it — with the partition present esp_wifi_init does not panic and the scan works. The partition stays: it is where the driver writes its calibration on the first boot. The C6's table carries a phy_init for the same reason.

The tables are named after the board: scripts/iot-image.sh has always looked for partitions/<board>.csv, and the layout is a board fact anyway. A 6 MB slot does not fit inside espflash's assumed 4 MB, so every S3 flash and image task passes --flash-size 16mb. The C6's table does not move: 1 MB holds its largest image, the probe, at 597,264 B. It is still a file — the image task and the flash task then have exactly one place that knows the layout.

Where a credential lives (the creds partition)

esp-storage 0.10 plus a slot format of our own, and not NVS: NVS is another blob with its own key-value semantics, where what has to be stored here is a fixed-length list — a format we hold ourselves is one we can read a line at a time.

The partition. Both boards' tables gain creds,data,undefined,,0x2000,, immediately after factory, and the three partitions that were already there do not move. [measured] checked offline (espflash partition-table --to-binary <csv> -o pt.bin, then --to-csv pt.bin): creds lands at 0x610000 on the S3 and 0x110000 on the C6, and factory is still at 0x10000. The two 4 KiB slots (8 KiB) are what writing the slots in turn needs: a save writes only the slot the last one did not, and a read takes the record with the larger sequence — power lost halfway through a write leaves the other slot's older copy, never half a record. The subtype has to be spelled as a name (undefined = DATA_UNDEFINED, 0x06): in hex, esp-idf-part panics on an unwrap (settled without flashing, see still-to-do 5's ②).

The format. core/src/drivers/credentials.rs. A record is a 12-byte header (magic VLNC, a version, a count, a body length) plus 1 + 32 + 1 + 64 + 2 bytes per network plus a 4-byte CRC, RECORD_BYTES = 1016, with two const _: () = assert!(...) pinning that it fits one sector; nine host tests pin the slot rules, a save interrupted by power loss, and how a bad CRC reads.

Features and where each layer sits

wifi is a component feature (module axis): one file, one module in iot-bsp-esp, gated once in components/mod.rs, aggregated into both board features (both boards have a radio soldered on). iot-core has no cfgs — the capability arrives through the composition point (HasWifi). components/wifi.rs is itself chip-agnostic: it takes only peripherals::WIFI and the driver's types, and it now compiles for each part.

Station's methods return impl Future (RPITIT) and deliberately do not carry + Send: the product joins those futures with input/render/control/feed on one task stack with no spawn. (Speaker does need Send because its feed runs on a separate higher-priority executor.)

take_wifi() cannot happen inside Board::new: the driver's start needs the scheduler running, and esp_rtos::start() belongs to the app's entry point, so the board hands over a peripheral, not a station.

iot-chip-esp's two chip features each forward five chip features of their own (esp-hal, esp-rtos, esp-println, esp-backtrace, esp-bootloader-esp-idf), with the console as a separate axis (console-auto / console-uart) the app forwards to. The reason: those three crates' build scripts each demand exactly one chip feature and a console, all of which an app used to supply, so any build without an app in it died inside someone else's build script — which is what iot-feature-check.sh hit the first time it reached the wifi entry. That is features.md rule 5: name every part you read.

The gesture cut: the delay was in the classifier, not the panel

[test] Touch is now Press / Tap (fired on the lift that resolves it) / Swipe / LongPress / Ghost only: GestureEvent::DoubleTap and TripleTap are gone from the vocabulary, and the two counters in TouchDiagnostics went with them.

The delay's root cause was a click being held in the mouth: the old TouchGestures parked a short lift in a chamber (PendingTap) and published it only in the tick that found the DOUBLE_CLICK_WINDOW_MS = 400 window expired — so every click waited up to 400 ms to be seen, and the page reacted 400 ms late with it. With touch multi-tap gone, Tap is published on the sample whose lift resolved it. The multi-click window stays where it belongs, on the hardware button: the triple click is the only way to change page, and that is a real button with its own window — still 400 ms.

GestureEvent::Tap carries at_ms (the lift's clock) and reports the down edge (down_x/down_y) instead of the release coordinates, because the panel is coarse and a release drifts. The keyboard uses at_ms to read a second tap inside 800 ms as "the next candidate" rather than "another character". TouchGestures' queue went from 2 slots to 4 at the same time (one sample can resolve at most one gesture per contact, two contacts, plus the run's single phantom pulse), dropping the oldest when full.

Typing along the panel's own path ([measured], 2026-10-16, late)

Exactly one stretch of "tap a row → type the passphrase → OK" can be reached through the glass: the coordinates travelling from the controller into a GestureEvent. Everything else is decided in the page's own coordinates, so a build can be made to tap itself at the cells it draws. An IOT_PANEL_BENCH build (crates/app/src/panel.rs) makes credentials_from_build() return None, so the product comes up on the "wait for the keyboard to name one" arm; then PanelBench publishes one tap per pass of the render loop, into the path a finger's taps take — intent::translate and the same INTENT_BUS ring.

One tap a pass rather than the whole run at once: the ring holds 8 slots, and a tap is applied only by the next pass's drain, so only the pass after that can decide the next tap against the state it produced. Tapping a saved row joins it with the copy the device keeps ([measured], 2026-10-17, fifth run)

Tapping a row this device has saved (the one drawn with *) joins it with the copy of the passphrase the device keeps in creds, instead of asking for it again. This row is where the two ownerships on the credential path part: the store of passphrases has exactly one owner, the network task (SavedNetworks never enters DeviceState — under the S3's static-memory wall those 980 B cannot become a value, see "Where a credential lives"), while all the page can say is which network and never what its passphrase is; so a tap on the page hands over only a name, and the answer (does the store have it, will it connect) comes from the radio.

  • The request is one plane with two shapes. CredentialPlane/CREDENTIALS are renamed JoinPlane/JOIN, and the message goes from Credentials to JoinRequest::{Typed(Credentials), Held(Ssid)} — two degrees of "how much help" for one request, still one single-slot plane (no second plane, no extra select arm). DeviceState.credential therefore becomes DeviceState.join: Option<JoinRequest> (take_join()): one field still, four bytes wider at most (Credentials is already the wider of the two variants), and no new static.
  • With no copy in the store, the page is told. The network task reads that plane in two places (setup's own top, and hold's window once the link is up) and both go through one asked_for(): Typed is used straight away (Provenance::Named); Held(name) goes through SavedNetworks::copy_of(name) — found, that copy is used (Provenance::Stored); not found, BusinessIntent::NoCopy(name) goes out (over the existing INTENT_BUS, the same road a Link report takes). The page's no_copy() acts only if the name is the one currently selected (a row tapped since is a newer question, and the stale answer is dropped) and raises the keyboard.
  • A refusal does not end in a loop. That copy can be refused too (the access point changed its passphrase). refused then behaves as before, and reopen_entry adds one thing: a selected row with no draft gets an empty one. The keyboard is drawn over the draft and the strip is hidden by the keyboard, so "a keyboard over no draft" is a page with nothing to press — and this row is exactly the one that would only ever be tapped a second time (tap it → the store's copy → refused → no keyboard → the only thing left to tap is that row again). Filling in an empty draft is the only way out of that loop, and it is the one place reopen_entry creates a draft.
  • The write test parts with it (Provenance): a passphrase from the build or from the panel is something the device learned, and it is written the moment the association succeeds (as before); the copy the store handed over is something the device already has, and it is not written. That also fixes a pointless write: the boot read's entry used to rewrite itself on every boot (two slots in turn means an erase and a program), which it no longer does; the price is that joining a saved row does not move it to the front of the saved list (so remember's promotion now only happens for a passphrase typed into the panel again).

The answer reaches the phone before setup mode ends

provision::serve returns Infallible, so in configure it races the panel's own path (setup_credential) through select: whichever names a credential first ends setup mode, the page's future is dropped with the select, and the access point goes down with its Runner. The credential travels the existing JOIN plane, so hold, the store and Provenance are reused unchanged — the page and the panel are the same path at the level of "where a credential came from".

The page publishes the credential only after writing the answer and waiting for the peer to acknowledge it (TcpSocket::flush, semantics read off tcp.rs and its docs in embassy-net 0.9.1). That is not caution; it is a race that loses every time: publishing to JOIN means select resolves at once and the page's future goes with the AP's Runner, so there is no next interface.poll — bytes sitting in the socket's buffer that never reached the medium vanish with the stack, and the phone sees a request that is never answered. /submit therefore answers with the done page inline in a 200 rather than redirecting to /done: a redirect needs a second request, and the stack that second request would wait on is already gone.

An idle exit, and the /exit that is still not built

The previous version of this section said "the AP stays up until somebody hands over a credential": the reference firmware's "reopen the AP after a while" and its /exit (78__esp-wifi-connect in ../xiaozhi-esp32) both read as identity operations. The first half stopped being true once setup mode became two front ends — the access point is now a front end raised for a phone, and one left up with nobody reading it is a configurable device for anyone in range; "reopen it" is still meaningless, because the answer is to take it down:

  • SETUP_IDLE_MS = 180_000: the clock starts when the access point front comes up and restarts with every request the page answers (provision::page_read() is a latest-value window, see page_idle). A phone filling the form in is not an idle access point.
  • The clock is always armed (page_idle(), no more armed): a board with a screen goes back to the panel front; a board without one goes back to the network it keeps (return None, link() associates again); a board with neither (no screen, no saved network) takes the access point down too and lands in browsing()'s offline state. The old "neither → no clock" exception is gone with the third cut of the entry: a board with a screen also gets in through the offline page's AP cell, a board without one only through the explicit reset-then-hold, and a factory device's open access point should not keep beaconing (see "Getting back to setup: hold BOOT on the splash page").
  • /exit is still not built: the page has no place for it, the panel's LEAVE/CLOSE/CANCEL say the same thing more completely, and the C6's way in is the hold on the splash page (see "Getting back to setup: hold BOOT on the splash page"), not a link in the page. abort() straight after the answer: the RST throws away what the phone has not read ([measured], 2026-10-20, evening)

What came back from the bench was an occasional ERR_CONNECTION_RESET: the page sometimes failed to appear, and reloading fixed it. Every one of those runs is Get / answered Ok, 15,425 B of body, in 88–196 ms on the device's side — the bytes really were written, and what was wrong is how the connection ended:

  • close() + flush() only waits for our own FIN to be acknowledged (FinWait2). The peer has not sent its FIN, which means it may still be reading.
  • The abort() right after sets the socket Closed; the stack sees remote_endpoint still there and sends a RST (the rst_pending test in flush()).
  • A RST makes the peer's kernel discard receive-queue bytes its application has not read yet — and the browser reports ERR_CONNECTION_RESET.

Three things beside it: 0 B answers (generate_204, the /mmtls 302) never failed once (one segment, no "not read yet" window); a large page takes several segments every time; both boards share this code, so both boards fail.

The first fix was wrong, and usefully so: waiting for the peer's FIN before releasing the socket, bounded at 500 ms, brought ERR_CONNECTION_REFUSED straight back from the bench. A socket waiting for a FIN is not listening: one of the three page sockets sits in that wait, the phone opens six connections per reload, and by the time the page's own connection is fourth in line there is no listener left, so its SYN is answered with a RST. Those minutes read exactly that way: three Get / lines, everything else generate_204 retries.

The measurement settled what the wait costs: the peer's FIN is already in when flush() returns (TimeWait after 0 ms, 451 of 455 connections), so waiting for it costs nothing; the bound came down to 100 ms, which 4 of 455 reached (still FinWait2, and that RST lands long after the peer stopped reading). Accepted on the bench: 55 page requests, 0 failures (could not accept 0, did not finish 0).

The same build turned send's silent Ok(0) into an answer stopped N B short: it catches three peer-side resets mid-body (the body stopped at 9,171 of 15,710 B), which used to be silent. CONNECTION_TIMEOUT came down from 10 s to 3 s as well: a request that only half arrived must not hold one of three page sockets for ten seconds (a page takes ~100 ms).

One hypothesis the same logs overturned: the scan was worked on first — every answered request raised PAGE_READ, and the survey's pause restarted on seeing it, on the grounds that a per-channel scan takes the radio off the access point's channel (a round ≈1.15 s against a 5 s pause, so the first few rounds spent ~19% of the time off-channel). It did take effect: zero survey found lines across nine reloads, and the rounds either side moved from 31 s to 47 s. The page failed anyway, so the scan was not the cause. The gate stays (a radio should not scan while somebody is reading a page), but it is not what fixed this.

  • Two fronts, not two paths: both share setup_credential, SurveyHistory, the list, the page, JOIN/FORGET/CANCEL; Front only decides which one is open. Splitting the code would make "switch back" a second implementation.
  • The station makes and holds the passphrase: begin_setup(ssid, secured) says which kind of AP to raise in one call, and status() reports setup_password. The panel reads it off the link status and draws it; the page never sees it, and the log records its length only, never its value.
  • SetupPass is a fixed-width narrow type ([u8; 10]), not an Ssid: the link status is copied every window, and a 32-byte name field holding a 10-byte value is 22 bytes the main task pays for nothing. It is also one of the ways this round pays for itself on the static wall (table below).
  • The alphabet drops 0/o/1/l: 23456789abcdefghjkmnpqrstuvwxyz, 31 symbols × 10 characters ≈ 49.5 bits. Copying that off a 320 px line into a phone's keyboard, look-alike characters are the only place it goes wrong.
  • The default passphrase depends on the entry, and is not remembered: the splash page's BOOT hold still raises an open AP, so a phone joins by tapping the network's name. PASS/NO PASS last for one visit; going away and back restores the entry's default. The C6 has no screen to show a passphrase, so it can only be open. The price is that the splash entry takes anyone in range for 180 s and the form is plain text; the running entry at least costs a passer-by the ten characters read off the panel.
  • CLOSE and CANCEL are different things: the box's right answer CLOSE only takes the AP down (back to the panel front); the strip's left cell CANCEL leaves setup mode to rejoin the saved network. The latter is drawn only when there is a way back (setup_cancellable); with no saved network the panel front's left cell becomes SCAN and the access point front's strip is one PANEL box — a blank device goes panel → access point → panel without ever touching "leave".
  • A stray tap in the box does not take the AP down: answer_at returns None outside the two answers, so the strip underneath still answers. This front has no "any tap dismisses", because a finger wandering across the box must not tear down the AP a phone is being walked onto.
  • The access point front does not survey on a clock: survey_pause_after(Front::AccessPoint, …) returns None — not a zero-length pause but no clock at all. Entering the front surveys once to fill the page; after that only the page's own RESCAN asks for a round.

It prices the one thing the access point front costs that the panel front does not — a network anyone in range can join. The price paid for that is discoverability: a device straight out of the box is invisible in a phone's list until somebody taps AP on the panel. A board with no panel has no cell to tap, so its way in is the reset-then-hold on the splash page (see the third cut), and a device out of the box is just as invisible on it.

"One reload is one connection" counted the document and not what the phone opens beside it: preconnects and the system's connectivity check send their SYNs within milliseconds, and SETUP_SOCKETS = 5 was DHCP 1 + DNS 1 + the page's 3. The fourth SYN finds no listener and the stack answers it with a RST, which the app never sees; Chrome marks the host as refusing connections and drops the two it had already opened (those are the two ConnectionReset lines).

Three changes:

  1. A phone's own Connection: close (Request::close, including a comma list that names close) or a request that names a network (Action::Join, the access point goes down right after the answer) ends it. A reload therefore reuses the connection it has instead of spending a listener. Pipelining is not read: a second request in the same segment is dropped with the connection's buffer, and no browser sends one.
  2. The page's listeners 3 → 6 (PAGE_SOCKETS = 6, SETUP_SOCKETS = 2 + PAGE_SOCKETS = 8): six is Chrome's own per-host ceiling, and it covers this burst of probe + preconnects + page.
  3. PENDING_TIMEOUT 1 s → 500 ms: a preconnect that never says anything hands its listener back sooner.

The rules:

  • SPLASH_MS = 1_500. Down from 3 s: the long-press threshold is 600 ms, so 1.5 s still fits a full hold, while a finger that just left reset can already reach the button; anything longer only makes every boot wait. The window is "begin the hold within 1.5 s", not "finish it within 1.5 s".
  • What counts is the press starting inside the window, not the release: when the clock runs out with a finger still down (InputSource::held(), including a release still in debounce), the splash waits for the release before closing (app/src/input.rs). A press at 1.4 s released at 2.1 s still counts; the clock does not pull the page out from under the finger.
  • One-shot is structural: Splash is not in CYCLE, next_page(Splash) answers Ambient, with_boot_page refuses it, and the only exit is the input task's BusinessIntent::SplashOver when the clock runs out (retried on the next tick if the bus is full). No gesture can get back to the page once the device has booted.
  • The landing is boot_page unless the hold asked: with_boot_page() still only records the page the splash lands on (the build input IOT_BOOT_PAGE, default Ambient; a page the wiring cannot back falls back to Ambient). SplashOver reads setup_wanted: asked for and the board wired a network means Network, anything else means boot_page. The splash itself never writes state.page, so a bench build with IOT_BOOT_PAGE=network still lands on the network page.
  • No link is built during the splash ([measured]): the first thing link() does is wait on PAGE.wait_for_splash_end(); until it resolves, neither a credential is read nor the radio touched — the splash window produces no joining/leaving line. When the request is there the path goes straight into Front::AccessPoint, with no association at all; an "associate, then tear down" implementation would leave two lines in that window and put the access point front 2–3 s later.
  • No credentials means an offline device: when first_saved() is empty, browsing() takes the device. It scans only while PAGE.shows_list() (the panel sitting on Network), stops when the page leaves, and only JOIN leads to hold — which is where the write happens. No setup mode, no access point: an unwrapped device is invisible in a phone's list. The panel page still carries both cells, and AP is what raises the access point. The C6 has no panel, so configuring it still means reset, then hold BOOT on the splash; that is its only way in.
  • The panel's page is resident: scanning, the list, the keyboard and JOIN were split out of the setup loop (setup_credential), and link.setup now means the page is on the setup face: the panel front raises no access point, the access point front does. On an S3 with no credentials, three taps to Network give a live list (browsing()) with SCAN | AP; tapping AP raises it, and a row picked sends JOIN, which hold receives.
  • The ways in remain: the offline page's AP cell, the panel's LEAVE on a live link (Hold::Left) and a saved credential that is refused (Hold::Refused) all enter setup mode — each is the finger's own doing.
  • The idle clock is always armed: page_idle() no longer takes armed; the access point front starts 180 s, every page request restarts it, and the exit goes back to the panel front or, on a board without one, to the saved network. The old "no screen and nothing saved → no clock" exception is gone: a board with no screen gets in only by reset-then-hold, while a board with a panel also has the offline page's AP cell, and a factory device's open access point should not keep beaconing.
  • A board with a screen draws three lines (VANLING / HOLD BOOT / SETUP, stamp_splash in bsp-esp), 3 × FONT_H apart and centred from width/height. A board without a screen (the C6) has no page to look at; the state still moves, and the Boot press latches the same request.

fast_connect (new in this cut, [test]):

  • Every saved network also carries a LinkHint { bssid: [u8; 6], channel: u8 } (NONE = unknown). The pure-logic part (host-testable)

Three rules in iot-core::drivers::network are product decisions rather than plumbing, so they sit where a test can pin them:

  • A scan list is ranked, not raw: dedupe on BSSID keeping the strongest report, order by signal, truncate to 8. Same-name access points are separate networks — a phone shows both — so the identity is the BSSID, not the name.
  • An SSID is bytes. 802.11 allows arbitrary octets and the panel's glyph table is printable ASCII, so whether a name can be drawn is one decision with a fallback (draw the BSSID instead). A non-ASCII name is still carried byte for byte — connecting needs it — and only its drawing fails.
  • A round's rhythm (a 5 s round, an empty round retried after 1 s up to three in a row, and a rest stretched to 15 s and then 30 s while nobody acts) is the same kind of policy, so it lives there too — see "The rhythm of a round".

Credentials::from_text rejects an over-long passphrase rather than truncating it, because the driver rejects it too and a truncated passphrase authenticates against nothing while reading as "wrong password".

Credentials come from build-time environment variables (IOT_WIFI_SSID / IOT_WIFI_PSK, read with option_env!) rather than a secret store: a bench image should say which network it joins, and a value compiled in is a value in the build command line. The product's credentials are typed on the panel and kept in the creds partition (see "Where a credential lives"); they must never be compiled into firmware. A build input outranks the stored list: a build that names a network has that one path to try (changing it means changing the build), where the stored list is the answer to "this device has been set up".

  • iot:flash is now an explicit espflash flash --chip esp32c6 --flash-size 8mb --partition-table partitions/esp32c6-devkitc-1.csv --monitor, with moon.yml saying why cargo run cannot carry the table.
